Web developers often treat the browser as a **black box** that magically transforms HTML, CSS, and JavaScript into interactive web applications. In truth, a modern web browser like Chrome ([Chromium](https://www.chromium.org/chromium-projects/)), Firefox ([Gecko](https://firefox-source-docs.mozilla.org/overview/gecko.html)) or Safari ([WebKit](https://webkit.org/)) is a complex piece of software. It orchestrates networking, parses and executes code, renders graphics with GPU acceleration, and isolates content in sandboxed processes for security.Web 开发者常常将浏览器视为一个黑盒，它能神奇地将 HTML、CSS 和 JavaScript 转化为交互式网页应用。实际上，像 Chrome（Chromium）、Firefox（Gecko）或 Safari（WebKit）这样的现代网络浏览器，是一套复杂的软件系统。它协调网络通信、解析并执行代码、利用 GPU 加速渲染图形，并通过沙盒进程隔离内容以确保安全。

This article dives into **how modern browsers work** - focusing on **Chromium**'s architecture and internals, while noting where other engines differ. We'll explore everything from the networking stack and parsing pipeline to the rendering process via [Blink](https://www.chromium.org/blink/), JavaScript engine via [V8](http://v8.dev/), module loading, multi-process architecture, security sandboxing, and developer tooling. The goal is a developer-friendly explanation that demystifies what happens behind the scenes.本文将深入探讨现代浏览器的工作原理——重点聚焦 Chromium 的架构与内部机制，同时指出其他引擎的差异之处。我们将全面解析从网络栈、解析管道到 Blink 渲染过程、V8 JavaScript 引擎、模块加载、多进程架构、安全沙盒以及开发者工具等各个环节。目标是以开发者友好的方式，揭开浏览器幕后运作的神秘面纱。

## Networking and Resource Loading网络与资源加载

![Image](https://pbs.twimg.com/media/HLOMmEWbAAA3ga_?format=jpg&name=large)

Every page load begins with the browser's networking stack fetching resources from the web. When you enter a URL or click a link, the browser's UI thread (running in the "[browser process](https://www.chromium.org/developers/design-documents/multi-process-architecture/)") kicks off a navigation request.每次页面加载，都始于浏览器的网络栈从网络获取资源。当你输入网址或点击链接时，浏览器 UI 线程（运行于"浏览器进程"中）会发起一次导航请求。

> The **browser process** is the main, controlling process that manages all other processes and the browser's user interface. Everything that happens outside of a specific web page tab is controlled by the browser process.浏览器进程是主要的控制进程，负责管理所有其他进程及浏览器的用户界面。所有发生在特定网页标签页之外的操作，均由浏览器进程控制。

The steps include:具体步骤包括：

**URL parsing and security checks**: The browser parses the URL to determine the scheme (http, https, etc.) and target domain. It also decides if the input is a search query or URL (in Chrome's omnibox, for example). Security features like blocklists may be checked here to avoid phishing sites.URL 解析与安全检查：浏览器解析 URL 以确定协议（http、https 等）和目标域名，同时判断输入内容属于搜索查询还是网址（例如 Chrome 的地址栏）。此阶段可能启用安全功能（如黑名单检测）以防范钓鱼网站。

**DNS lookup**: The network stack resolves the domain name to an IP address (unless it's cached). This may involve contacting a DNS server. Modern browsers might use OS DNS services or even DNS over HTTPS (DoH) if configured, but ultimately they obtain an IP for the host.DNS 查询：网络栈将域名解析为 IP 地址（除非已缓存）。此过程可能涉及联系 DNS 服务器。现代浏览器可使用操作系统 DNS 服务，或根据配置采用 DNS over HTTPS（DoH）协议，但最终都会获取目标主机的 IP 地址。

**Establishing a connection**: If no open connection to the server exists, the browser opens one. For HTTPS URLs, this includes a TLS handshake to securely exchange keys and verify certificates. The browser's network thread handles protocols like TCP/TLS setup transparently.建立连接：若与服务器无现有连接，浏览器将新建连接。对于 HTTPS 网址，此过程包含 TLS 握手以安全交换密钥并验证证书。浏览器的网络线程会透明处理 TCP/TLS 等协议的建立流程。

**Sending the HTTP request**: Once connected, an HTTP GET request (or other method) is sent for the resource. Browsers today default to HTTP/2 or HTTP/3 if the server supports it, which allows multiplexing multiple resource requests over one connection. This improves performance by avoiding the old limit of ~6 parallel connections per host (HTTP/1.1). For example, with HTTP/2 the HTML, CSS, JS, images can all be fetched concurrently on one TCP/TLS link, and with HTTP/3 (over QUIC UDP) setup latency is further reduced.发送 HTTP 请求：连接建立后，浏览器会向资源发送 HTTP GET 请求（或其他方法）。若服务器支持，现代浏览器默认使用 HTTP/2 或 HTTP/3 协议，这允许在单个连接上多路复用多个资源请求。通过避免旧版每个主机仅限~6 个并行连接（HTTP/1.1）的限制，性能得以提升。例如，使用 HTTP/2 时，HTML、CSS、JS 和图片可在单个 TCP/TLS 链路上并发获取；而采用 HTTP/3（基于 QUIC UDP 协议）时，连接建立延迟将进一步降低。

**Receiving the response**: The server responds with an HTTP status and headers, followed by the response body (HTML content, JSON data, etc.). The browser reads the response stream. It may need to sniff the MIME type if the Content-Type header is missing or incorrect, to decide how to handle the content. For example, if a response looks like HTML but isn't labeled as such, the browser will still try to treat it as HTML (per permissive web standards). There are security measures here too: the network layer checks Content-Type and may block suspicious MIME mismatches or disallowed cross-origin data (Chrome's CORB - Cross-Origin Read Blocking - is one such mechanism). The browser also consults Safe Browsing or similar services to block known malicious payloads.接收响应：服务器返回 HTTP 状态码和头部信息，随后是响应体（HTML 内容、JSON 数据等）。浏览器读取响应流。如果缺少或错误设置了 Content-Type 头部，浏览器可能需要嗅探 MIME 类型，以决定如何处理内容。例如，如果响应看起来像 HTML 但未标记为 HTML，浏览器仍会尝试将其视为 HTML（遵循宽松的 Web 标准）。这里也存在安全措施：网络层会检查 Content-Type，并可能阻止可疑的 MIME 类型不匹配或不允许的跨域数据（Chrome 的 CORB——跨域读取阻止——就是此类机制之一）。浏览器还会咨询安全浏览或类似服务，以阻止已知的恶意负载。

**Redirects and next steps**: If the response is an HTTP redirect (e.g. 301 or 302 with a Location header), the network code will follow the redirect (after informing the UI thread) and repeat the request to the new URL. Only once a final response with actual content is obtained does the browser move on to processing that content.重定向与后续步骤：如果响应是 HTTP 重定向（例如带有 Location 头部的 301 或 302 状态码），网络代码将遵循重定向（在通知 UI 线程后），并向新 URL 重复请求。只有在获得包含实际内容的最终响应后，浏览器才会继续处理该内容。

All these steps happen in the network stack, which in Chromium is run in a dedicated Network Service (now typically a separate process, as part of Chrome's "[servicification](https://www.chromium.org/servicification/)" effort). The browser process's network thread coordinates the low-level work of socket communication, using the OS networking APIs under the hood. Importantly, this design means the renderer (which will execute the page's code) doesn't directly access the network - it asks the browser process to fetch what it needs, a security win.所有这些步骤都发生在网络栈中，在 Chromium 中，网络栈运行在专用的网络服务中（作为 Chrome“服务化”工作的一部分，现在通常是一个独立的进程）。浏览器进程的网络线程利用底层操作系统网络 API 来协调套接字通信的低级工作。重要的是，这种设计意味着渲染器（将执行页面代码）不会直接访问网络——它会请求浏览器进程获取所需内容，这是一项安全优势。

**Speculative Loading and Resource Optimization推测加载与资源优化**

Modern browsers implement sophisticated performance optimizations in the networking stage. Chrome will proactively perform a DNS prefetch or open a TCP connection when you hover over a link or start typing a URL (using the Predictor or preconnect mechanisms) so that if you click, some latency is already shaved off. There's also HTTP caching: the network stack can satisfy requests from the browser cache if the resource is cached and fresh, avoiding a network trip.现代浏览器在网络阶段实现了复杂的性能优化。当您悬停在链接上或开始输入 URL 时，Chrome 会主动执行 DNS 预取或打开 TCP 连接（使用预测器或预连接机制），这样一旦您点击，部分延迟就已经被消除。此外还有 HTTP 缓存：如果资源已缓存且未过期，网络栈可以直接从浏览器缓存中满足请求，从而避免网络往返。

**Preload scanner operation**: Chromium implements a sophisticated [preload scanner](https://web.dev/articles/preload-scanner) that tokenizes HTML markup ahead of the main parser. When the primary HTML parser is blocked by CSS or synchronous JavaScript, the preload scanner continues examining the raw markup to identify resources like images, scripts, and stylesheets that can be fetched in parallel. This mechanism is fundamental to modern browser performance and operates automatically without developer intervention. The preload scanner cannot discover resources injected via JavaScript, making such resources likely to be loaded consecutively rather than concurrently.预加载扫描器操作：Chromium 实现了一个复杂的预加载扫描器，该扫描器会在主解析器之前对 HTML 标记进行分词处理。当主 HTML 解析器被 CSS 或同步 JavaScript 阻塞时，预加载扫描器会继续检查原始标记，以识别可并行获取的图像、脚本和样式表等资源。这一机制是现代浏览器性能的基础，无需开发者干预即可自动运行。预加载扫描器无法发现通过 JavaScript 注入的资源，因此这类资源更可能被顺序加载而非并发加载。

**Early Hints (HTTP 103)**: [Early Hints](https://developer.chrome.com/docs/web-platform/early-hints) allows servers to send resource hints while generating the main response, using HTTP 103 status codes. This enables preconnect and preload hints to be sent during server think-time, potentially improving Largest Contentful Paint by several hundred milliseconds. Early Hints are only available for navigation requests and support preconnect and preload directives, but not prefetch.HTTP 103 早期提示：早期提示允许服务器在生成主响应时，通过 HTTP 103 状态码发送资源提示。这使服务器在思考阶段即可发送预连接和预加载提示，有望将最大内容绘制时间缩短数百毫秒。早期提示仅适用于导航请求，支持预连接和预加载指令，但不支持预获取。

**Speculation Rules API**: [The Speculation Rules API](https://developer.chrome.com/docs/web-platform/implementing-speculation-rules) is a recent web standard that allows defining rules to dynamically prefetch and prerender URLs based on user interaction patterns. Unlike traditional link prefetch, this API can prerender entire pages including JavaScript execution, leading to near-instant load times. The API uses JSON syntax within script elements or HTTP headers to specify which URLs should be speculatively loaded. Chrome has limits to prevent overuse, with different capacity settings based on urgency levels.推测规则 API：推测规则 API 是一项最新的网络标准，允许根据用户交互模式定义规则，动态预取和预渲染 URL。与传统的链接预取不同，该 API 能够预渲染包括 JavaScript 执行在内的完整页面，从而实现近乎即时的加载速度。该 API 通过 script 元素或 HTTP 标头中的 JSON 语法来指定应进行推测性加载的 URL。Chrome 设置了防止过度使用的限制，根据紧急程度采用不同的容量配置。

**HTTP/2 and HTTP/3**: Most Chromium-based browsers and Firefox support HTTP/2 fully, and [HTTP/3](https://alexandrehtrb.github.io/posts/2024/03/http2-and-http3-explained/) (based on QUIC) is also widely supported (Chrome has it enabled by default for supporting sites). These protocols improve page load by allowing concurrent transfers and reducing handshake overhead. From a developer perspective, this means you may no longer need sprite sheets or domain sharding tricks - the browser can efficiently fetch many small files in parallel on one connection.HTTP/2 与 HTTP/3：大多数基于 Chromium 的浏览器和 Firefox 已完全支持 HTTP/2，而 HTTP/3（基于 QUIC 协议）也得到广泛支持（Chrome 默认对支持该协议的网站启用）。这些协议通过允许并发传输和减少握手开销来提升页面加载速度。从开发者角度看，这意味着你可能不再需要使用精灵图或域名分片技巧——浏览器可以在单个连接上高效并行获取多个小文件。

**Resource prioritization**: The browser also prioritizes certain resources over others. Typically, HTML and CSS are high priority (as they block rendering), scripts might be medium (or high if marked defer/async appropriately), and images maybe lower. Chromium's network stack assigns weights and can even cancel or defer requests to prioritize what's needed for an initial render. Developers can use [link rel=preload](https://web.dev/articles/preload-critical-assets) and [Fetch Priority](https://web.dev/articles/fetch-priority) to influence resource prioritization.资源优先级：浏览器还会对某些资源进行优先级排序。通常 HTML 和 CSS 优先级最高（因为它们会阻塞渲染），脚本可能为中等优先级（若正确标记 defer/async 则可能为高优先级），而图片优先级可能较低。Chromium 的网络栈会分配权重，甚至能取消或延迟请求，优先处理首屏渲染所需的资源。开发者可通过 \`link rel=preload\` 和 Fetch Priority 来影响资源优先级。

By the end of the networking phase, the browser has the initial HTML for the page (assuming it was an HTML navigation). At this point, Chrome's browser process chooses a renderer process to handle the content. Chrome will often launch a new renderer process in parallel with the network request (speculatively) so that it's ready to go when the data arrives. This renderer process is isolated (more on multi-process architecture later) and will take over for parsing and rendering the page.网络阶段结束时，浏览器已获取页面的初始 HTML（假设是 HTML 导航）。此时，Chrome 的浏览器进程会选择一个渲染进程来处理内容。Chrome 通常会在网络请求的同时（推测性地）启动新的渲染进程，以便数据到达时能立即就绪。该渲染进程是隔离的（后续将详述多进程架构），并负责接管页面的解析与渲染工作。

Once the response is fully received (or as it streams in), the browser process commits the navigation: it signals the renderer process to take the stream of bytes and start processing the page. At this moment, the address bar updates and the security indicator (HTTPS lock, etc.) is shown for the new site. Now the action moves to the renderer process: parsing the HTML, loading sub-resources, executing scripts, and painting the page.一旦响应完全接收（或随着数据流逐步到达），浏览器进程便会提交导航：它通知渲染进程接收字节流并开始处理页面。此时，地址栏会更新，新站点的安全指示器（如 HTTPS 锁图标等）也会显示。随后操作转入渲染进程：解析 HTML、加载子资源、执行脚本以及绘制页面。

## Parsing HTML, CSS, and JavaScript解析 HTML、CSS 和 JavaScript

When the renderer process receives the HTML content, its main thread begins to parse it according to the HTML specification. The result of parsing HTML is the DOM (Document Object Model) - a tree of objects representing the page structure. Parsing is incremental and can interleave with network reading (browsers parse HTML in a streaming fashion, so the DOM can start being built even before the entire HTML file is downloaded).当渲染进程接收到 HTML 内容时，其主线程会根据 HTML 规范开始解析。解析 HTML 的结果是 DOM（文档对象模型）——一种表示页面结构的对象树。解析是增量式的，并且可以与网络读取交错进行（浏览器以流式方式解析 HTML，因此即使在完整 HTML 文件下载完成之前，DOM 也可以开始构建）。

![Image](https://pbs.twimg.com/media/HLOMqGBaEAAGwkI?format=jpg&name=large)

**HTML parsing and DOM construction**: HTML parsing is defined by the HTML Standard as a error-tolerant process that will produce a DOM no matter how malformed the markup is. This means even if you forget a closing \</p> tag or have nested tags incorrectly, the parser will implicitly fix or adjust the DOM tree so that it's valid. For example, \<p>Hello \<div>World\</div> will automatically end the \<p> before the \<div> in the DOM structure. The parser creates DOM elements and text nodes for each tag or text in the HTML. Each element is placed in a tree reflecting the nesting in the source.HTML 解析与 DOM 构建：HTML 解析由 HTML 标准定义为一种容错处理过程，无论标记格式多么不规范，都会生成一个 DOM。这意味着即使你忘记闭合\</p>标签或嵌套标签有误，解析器也会隐式修复或调整 DOM 树，使其保持有效。例如，\<p>Hello \<div>World\</div>会在 DOM 结构中自动在\<div>之前结束\<p>。解析器会为 HTML 中的每个标签或文本创建 DOM 元素和文本节点，每个元素都会按照源代码中的嵌套关系放置在树形结构中。

One important aspect is that the HTML parser may encounter resources to fetch as it goes: for instance, encountering a \<link rel="stylesheet" href="..."> will prompt the browser to request the CSS file (on the network thread), and encountering an \<img src="..."> will trigger an image request. These happen in parallel to parsing. The parser can keep going while those loads occur, with one big exception: scripts.一个重要的方面是，HTML 解析器在解析过程中可能会遇到需要获取的资源：例如，遇到\<link rel="stylesheet" href="...">会提示浏览器请求 CSS 文件（在网络线程上），而遇到\<img src="...">则会触发图片请求。这些操作与解析过程并行进行。解析器可以在这些加载过程中继续工作，但有一个重大例外：脚本。

**Handling \<script> tags**: If the HTML parser comes across a \<script> tag, it pauses parsing and must execute the script before continuing (by default). This is because scripts can use document.write() or other DOM manipulation that can alter the page structure or content that's still coming in. By executing immediately at that point, the browser preserves the correct order of operations relative to the HTML. The parser therefore hands off the script to the JavaScript engine for execution, and only when the script finishes (and any DOM changes it did are applied) can HTML parsing resume. This script execution blocking behavior is why including large \<script> files in the head can slow down page rendering - the HTML parsing can't continue until the script is downloaded and run.处理 \`\<script>\` 标签：当 HTML 解析器遇到 \`\<script>\` 标签时，会暂停解析并（默认情况下）必须先执行该脚本才能继续。这是因为脚本可能使用 \`document.write()\` 或其他 DOM 操作来改变尚未加载完成的页面结构或内容。通过在该位置立即执行脚本，浏览器能确保操作顺序与 HTML 的加载顺序保持一致。因此，解析器会将脚本交给 JavaScript 引擎执行，只有脚本执行完毕（及其产生的 DOM 变更生效后），HTML 解析才能恢复。这种脚本执行阻塞行为正是为什么在 \`\<head>\` 中引入大型 \`\<script>\` 文件会拖慢页面渲染——在脚本下载并运行完成前，HTML 解析无法继续。

However, developers can modify this behavior with attributes: adding [defer or async](https://web.dev/articles/efficiently-load-third-party-javascript) to a \<script> tag (or using modern ES module scripts) changes how the browser handles it. With async, the script file is fetched in parallel and executed as soon as it's ready, without pausing HTML parsing (the parse doesn't wait, and the script doesn't guarantee execution in original order relative to other async scripts). With defer, the script is fetched in parallel but execution is deferred until the HTML parsing is done (and will execute in the original order at that later time). In both cases, the parser isn't blocked waiting on the script, which is generally better for performance. ES6 modules (using \<script type="module">) are automatically deferred as well (and they can also use import statements - we'll cover module loading separately). By using these techniques, the browser can continue building the DOM without long pauses, making pages load faster.然而，开发者可以通过属性修改这一行为：在 \`\<script>\` 标签中添加 \`defer\` 或 \`async\`（或使用现代 ES 模块脚本）会改变浏览器的处理方式。使用 \`async\` 时，脚本文件会被并行获取，并在准备就绪后立即执行，不会暂停 HTML 解析（解析过程无需等待，且该脚本不保证按原始顺序相对于其他异步脚本执行）。使用 \`defer\` 时，脚本会被并行获取，但执行会推迟到 HTML 解析完成后（届时将按原始顺序执行）。这两种情况下，解析器都不会因等待脚本而阻塞，这通常更有利于性能。ES6 模块（使用 \`\<script type="module">\`）也会自动延迟执行（它们还可以使用 \`import\` 语句——我们将在模块加载部分单独介绍）。通过运用这些技术，浏览器可以持续构建 DOM 而无需长时间暂停，从而加快页面加载速度。

**CSS Parsing and the CSSOM**: Alongside HTML, CSS text must be parsed into a structure the browser can work with - often called the CSSOM (CSS Object Model). The [CSSOM](https://web.dev/articles/critical-rendering-path/constructing-the-object-model) is essentially a representation of all the styles (rules, selectors, properties) that apply to the document. The browser's CSS parser reads CSS files (or \<style> blocks) and turns them into a list of CSS rules (and lots of bloom filters etc to speed up style resolution). Then, as the DOM is being constructed (or once both DOM and CSSOM are ready), the browser will compute the style for each DOM node. This step is usually called style resolution or style calculation. The browser combines the DOM and CSSOM to determine, for each element, which CSS rules apply and what the final computed styles are (after applying the cascade, inheritance, and default styles). The output is often conceptualized as an association of each DOM node with a computed style (the resolved, final CSS properties for that element, e.g. an element's color, font, size, etc.).CSS 解析与 CSSOM：与 HTML 类似，CSS 文本必须被解析成浏览器可处理的结构——通常称为 CSSOM（CSS 对象模型）。CSSOM 本质上是文档中所有样式（规则、选择器、属性）的表示形式。浏览器的 CSS 解析器读取 CSS 文件（或\<style>代码块），将其转换为 CSS 规则列表（并生成大量布隆过滤器等结构以加速样式解析）。随后，在 DOM 构建过程中（或当 DOM 与 CSSOM 均就绪时），浏览器会为每个 DOM 节点计算样式。此步骤通常称为样式解析或样式计算。浏览器通过结合 DOM 与 CSSOM，确定每个元素适用的 CSS 规则及最终计算样式（经过层叠、继承和默认样式处理后的结果）。其输出通常被概念化为每个 DOM 节点与计算样式（该元素解析后的最终 CSS 属性，如颜色、字体、尺寸等）的关联关系。

It's worth noting that even without any author CSS, every element has default browser styles (the user-agent stylesheet). For example, a \<h1> has a default font-size and margin in practically all browsers. The browser's built-in style rules are applied with the lowest priority, and they ensure some reasonable default presentation. Developers can view computed styles in DevTools to see exactly what CSS properties an element ends up with. The style calculation step uses all applicable styles (user agent, user styles, author styles) to finalize each element's styling.值得注意的是，即使没有任何作者 CSS，每个元素都有默认的浏览器样式（用户代理样式表）。例如，在几乎所有浏览器中，\`\<h1>\` 都有默认的字体大小和外边距。浏览器内置的样式规则以最低优先级应用，确保提供合理的默认呈现效果。开发者可以在开发者工具中查看计算后的样式，准确了解元素最终具有哪些 CSS 属性。样式计算步骤会使用所有适用的样式（用户代理样式、用户样式、作者样式）来确定每个元素的最终样式。

**Render-blocking behavior**: While HTML parsing can proceed without CSS fully loaded, there is a [render-blocking relationship](https://web.dev/learn/performance/understanding-the-critical-path): browsers typically wait to perform the first render until CSS is loaded (for CSS in the \<head>). This is because applying an incomplete stylesheet could flash unstyled content. In practice, if a \<script> that is not marked async/defer appears before a CSS \<link> in HTML, it will additionally wait for the CSS to load before executing the script (since scripts may query style information via DOM APIs). As a rule of thumb, put stylesheet links in the head (they block rendering but are needed early) and put non-critical or large scripts with defer/async or at the bottom so they don't delay DOM parsing.渲染阻塞行为：虽然 HTML 解析可以在 CSS 完全加载前进行，但存在渲染阻塞关系：浏览器通常会等待 CSS 加载完成后才执行首次渲染（针对\<head>中的 CSS）。这是因为应用不完整的样式表可能导致无样式内容闪烁。实际上，如果 HTML 中未标记 async/defer 的\<script>出现在 CSS \<link>之前，该脚本会额外等待 CSS 加载完成后才执行（因为脚本可能通过 DOM API 查询样式信息）。经验法则：将样式表链接放在\<head>中（它们会阻塞渲染但需要尽早加载），将非关键或大型脚本使用 defer/async 属性或置于页面底部，以免延迟 DOM 解析。

Now the browser has (1) the DOM constructed from HTML, (2) the CSS rules parsed (CSSOM), and (3) the computed styles for each DOM node. These together form the basis for the next stage: layout. But before moving on, we should consider the JavaScript side in more detail - specifically how the JS engine (V8 in Chrome's case) executes code. We touched on script blocking, but what happens when the JS runs? We'll dedicate a later section to the internals of V8 and JS execution. For now, assume that as scripts run, they might modify the DOM or CSSOM (for example, calling document.createElement or setting element styles). The browser may have to respond to those changes by recalculating styles or layout as needed (which can incur performance costs if done repeatedly). The initial run of scripts during parsing often includes things like setting up event handlers, or maybe manipulating the DOM (e.g. templating). After that, the page is usually fully parsed and we move into layout and rendering.现在浏览器已经具备了：(1) 由 HTML 构建的 DOM 树，(2) 解析后的 CSS 规则（CSSOM），以及(3) 每个 DOM 节点的计算样式。这三者共同构成了下一阶段——布局——的基础。但在继续之前，我们需要更详细地探讨 JavaScript 层面——具体来说，JS 引擎（以 Chrome 的 V8 为例）是如何执行代码的。我们之前提到过脚本阻塞，但 JS 运行时究竟会发生什么？后续章节将专门介绍 V8 和 JS 执行的内部机制。目前只需知道：脚本运行时可能会修改 DOM 或 CSSOM（例如调用 document.createElement 或设置元素样式）。浏览器可能需要响应这些变化，重新计算样式或布局（若频繁操作将产生性能开销）。解析阶段的初始脚本执行通常包含事件处理器的设置或 DOM 操作（如模板渲染）。此后，页面通常完成解析，进入布局与渲染阶段。

## Styling and Layout样式与布局

At this stage, the browser's renderer process knows the structure of the DOM and each element's computed style. The next question is: where do all these elements go on the screen? How big are they? This is the job of layout (also known as "reflow" or "layout calculation"). In this phase, the browser calculates the geometry of each element - their size and position - according to the CSS rules (flow, box model, flexbox or grid, etc.) and the DOM hierarchy.在此阶段，浏览器的渲染进程已掌握 DOM 结构及各元素的计算样式。接下来的问题是：这些元素在屏幕上应如何分布？它们的大小是多少？这正是布局（又称"重排"或"布局计算"）的职责所在。在此阶段，浏览器会根据 CSS 规则（流式布局、盒模型、弹性布局或网格布局等）及 DOM 层级结构，计算每个元素的几何属性——即其尺寸与位置。

![Image](https://pbs.twimg.com/media/HLOMtgGagAAFMes?format=jpg&name=large)

**Layout tree construction**: The browser walks the DOM tree and generates a layout tree (sometimes called the render tree or frame tree). The layout tree is similar to the DOM tree in structure, but it omits non-visual elements (e.g. script or meta tags don't produce boxes) and may split some elements into multiple boxes if needed (for example, a single HTML element that is flowed across multiple lines might correspond to multiple layout boxes). Each node in the layout tree holds the computed style for that element and has information like the node's content (text or image) and computed properties that affect layout (like width, height, padding, etc.).布局树构建：浏览器遍历 DOM 树并生成布局树（有时称为渲染树或框架树）。布局树在结构上与 DOM 树相似，但会省略非视觉元素（例如 script 或 meta 标签不会生成盒子），必要时还会将某些元素拆分为多个盒子（例如跨多行排列的单个 HTML 元素可能对应多个布局盒子）。布局树中的每个节点都包含该元素的计算样式，并存储节点内容（文本或图像）及影响布局的计算属性（如宽度、高度、内边距等）相关信息。

During layout, the browser computes the exact position (x, y coordinates) and size (width, height) for each element's box. This involves algorithms defined by CSS specifications: for example, in a normal document flow, block-level elements stack top-to-bottom, each taking full width by default, whereas inline elements flow within lines and cause line breaks as needed. Modern layout modes like [flexbox](https://web.dev/learn/css/flexbox) or [grid](https://web.dev/learn/css/grid) have their own algorithms. The engine has to consider font metrics to break lines (so text layout involves measuring text runs), and it must handle margins, padding, border, etc. There are many edge cases (e.g. margin collapsing rules, floats, absolutely positioned elements that are removed from flow, etc.), making layout a surprisingly complex process. Even a "simple" top-to-bottom layout has to figure out line breaks in text which depend on available width and font sizes. Browser engines have dedicated teams and many years of development to handle layout accurately and efficiently.在布局过程中，浏览器会计算每个元素盒子的精确位置（x、y 坐标）和尺寸（宽度、高度）。这涉及 CSS 规范定义的算法：例如，在常规文档流中，块级元素自上而下堆叠，默认占据完整宽度；而内联元素则在行内流动，并根据需要换行。现代布局模式（如弹性盒或网格）拥有各自的算法。引擎需要考虑字体度量来实现换行（因此文本布局涉及测量文本运行），同时必须处理边距、内边距、边框等属性。存在大量边界情况（例如边距折叠规则、浮动元素、脱离文档流的绝对定位元素等），这使得布局成为一个异常复杂的过程。即便是"简单"的自上而下布局，也需要根据可用宽度和字体大小计算文本换行。浏览器引擎拥有专门团队和多年开发经验，以确保布局的准确性和高效性。

Some details about the layout tree:关于布局树的一些细节：

- Elements with display:none are omitted entirely from the layout tree (they don't produce any box). In contrast, elements that are simply not visible (e.g. visibility:hidden) do get a layout box (taking up space), just not painted later.具有 \`display:none\` 的元素会完全从布局树中移除（它们不会生成任何盒子）。相比之下，仅仅是不可见的元素（例如 \`visibility:hidden\`）仍会获得布局盒子（占据空间），只是后续不会被绘制。
- Pseudo-elements like ::before or ::after that generate content are included in the layout tree (since they do have visual boxes).像 \`::before\` 或 \`::after\` 这类生成内容的伪元素会被包含在布局树中（因为它们确实拥有视觉盒子）。
- The layout tree nodes know their geometry. For example, a \<p> element's layout node will know its position relative to the viewport and its dimensions, and have children for each line or inline box inside it.布局树中的节点知晓自身的几何信息。例如，一个 \`\<p>\` 元素的布局节点会知道它相对于视口的位置和尺寸，并且其子节点对应内部的每一行或内联盒子。

**Layout calculation**: Layout is typically a recursive process. Starting from the root (the \<html> element), the browser computes the size of the viewport (for \<html>/\<body>) and then lays out child elements within it, and so on. Many elements' sizes depend on their children or parent (e.g. a container might expand to fit children, or a child might be 50% of its parent's width). The layout algorithm often has to do multiple passes for things like floats or for certain complex interactions, but generally it proceeds in one direction (top-down) with possible backtracking if needed.布局计算：布局通常是一个递归过程。从根元素（\`\<html>\` 元素）开始，浏览器计算视口尺寸（针对 \`\<html>\`/\`\<body>\`），然后在其内部逐层布局子元素，以此类推。许多元素的尺寸取决于其子元素或父元素（例如，容器可能根据子元素自动扩展，或者子元素宽度可能设为父元素的 50%）。布局算法通常需要针对浮动元素或某些复杂交互进行多轮处理，但总体而言会沿单一方向（自上而下）推进，必要时可能进行回溯。

By the end of this stage, each element's position and size on the page is known. We can now conceptually think of the page as a bunch of boxes (with text or images inside). But we still haven't actually drawn anything on the screen yet - that's the next step, painting.在此阶段结束时，页面上每个元素的位置和大小都已确定。我们现在可以将页面概念性地视为一组盒子（内部包含文本或图像）。但我们实际上还没有在屏幕上绘制任何内容——这是下一步，即绘制。

However, one key concept: layout can be an expensive operation, especially if done repeatedly. If JavaScript later changes the size of an element or adds content, it can force a relayout of some or all of the page. Developers often hear advice about avoiding layout thrashing (like reading layout info in JS right after modifying DOM, which can force synchronous recalculation). The browser tries to optimize by noting what parts of the layout tree are "dirty" and only recomputing those. But worst-case, changes high up in the DOM could require recalculating the entire layout for large pages. This is why costly style/layout operations should be minimized for better performance.然而，一个关键概念：布局可能是一项昂贵的操作，尤其是在重复执行时。如果 JavaScript 后来更改了元素的大小或添加了内容，它可能会强制重新计算部分或整个页面的布局。开发者经常听到关于避免布局抖动的建议（例如在修改 DOM 后立即在 JS 中读取布局信息，这可能会强制同步重新计算）。浏览器会通过标记布局树中哪些部分“脏”并仅重新计算这些部分来尝试优化。但在最坏的情况下，DOM 中较高层的更改可能需要为大型页面重新计算整个布局。这就是为什么应尽量减少昂贵的样式/布局操作以获得更好性能的原因。

**Style and layout recap**: To summarize, from HTML and CSS the browser builds:样式与布局总结：总结来说，浏览器从 HTML 和 CSS 构建出：

- DOM tree - structure and contentDOM 树——结构和内容
- CSSOM - parsed CSS rulesCSSOM - 解析后的 CSS 规则
- Computed Styles - the result of matching CSS rules to each DOM node计算样式 - 将 CSS 规则匹配到每个 DOM 节点后的结果
- Layout tree - DOM tree filtered to visual elements, with geometry for each node布局树 - 过滤出可见元素的 DOM 树，包含每个节点的几何信息

Each stage builds on the last. If any stage changes (e.g. if a script alters the DOM or modifies a CSS property), the subsequent stages may need to update. For example, if you change a CSS class on an element, the browser may recalc style for that element (and children if inheritance changes), then might have to redo layout if that style change affects geometry (say display or size), then would have to repaint. This chain means layout and paint are dependent on up-to-date style, and so on. We'll discuss performance implications of this in the DevTools section (as the browser provides tools to see when these steps occur and how long they take).每个阶段都建立在前一阶段之上。如果任一阶段发生变化（例如脚本修改 DOM 或 CSS 属性），后续阶段可能需要更新。例如，当你更改元素上的 CSS 类时，浏览器可能需要重新计算该元素的样式（若继承关系改变则需计算子元素样式），若样式变化影响几何属性（如 display 或尺寸），则需重新布局，最后还需重新绘制。这种连锁反应意味着布局和绘制依赖于最新的样式信息，以此类推。我们将在 DevTools 部分讨论这对性能的影响（因为浏览器提供了工具来观察这些步骤何时发生及其耗时）。

With layout done, we move to the next major phase: painting.布局完成后，我们进入下一个主要阶段：绘制。

## Painting, Compositing, and GPU Rendering绘制、合成与 GPU 渲染

Painting is the process of taking the structured layout information and actually producing pixels on the screen. In traditional terms, the browser would traverse the layout tree and issue drawing commands for each node ("draw background, draw text, draw image at these coordinates"). Modern browsers still conceptually do this, but they often split the work into multiple stages and leverage the GPU for efficiency.绘制是将结构化的布局信息转化为屏幕像素的过程。传统意义上，浏览器会遍历布局树，为每个节点发出绘制指令（"在此坐标绘制背景、绘制文本、绘制图像"）。现代浏览器在概念上仍遵循这一流程，但通常会将工作拆分为多个阶段，并借助 GPU 提升效率。

![Image](https://pbs.twimg.com/media/HLOMxE6aIAAm-_3?format=jpg&name=large)

**Painting / Rasterization**: On the renderer's main thread, after layout, Chrome generates paint records (or a display list) by walking the layout tree. This is basically a list of drawing operations with their coordinates, much like an artist planning how to paint the scene: e.g. "draw rect at (x,y) with width W and height H and fill color blue, then draw text 'Hello' at (x2,y2) with font XYZ, then draw an image at …" and so on. This list is in the correct z-index order (so that overlapping elements paint correctly). For example, if an element has a higher z-index, its paint commands will come later (on top of) lower z-index content. The browser must consider stacking contexts, transparency, etc. to get the right ordering.绘画/光栅化：在渲染器的主线程上，布局完成后，Chrome 通过遍历布局树生成绘制记录（或称显示列表）。这本质上是一系列包含坐标的绘图操作指令，如同艺术家规划如何绘制场景：例如"在(x,y)处绘制宽度为 W、高度为 H 的蓝色填充矩形，然后在(x2,y2)处用 XYZ 字体绘制文本'Hello'，接着在(x3,y3)处绘制图像……"等等。该列表按正确的 z 轴顺序排列（确保重叠元素正确绘制）。例如，若某元素具有更高 z-index 值，其绘制指令将排在低 z-index 内容之后（即覆盖其上）。浏览器必须考虑层叠上下文、透明度等因素以确保正确排序。

In the past, browsers might have simply drawn each element directly to the screen in order. But that approach can be inefficient if parts of the page change (you'd have to repaint everything). Modern browsers instead often record these drawing commands and then use a compositing step to assemble the final image, especially when using GPU acceleration.过去，浏览器可能直接按顺序将每个元素绘制到屏幕上。但若页面局部发生变化，这种方式的效率会很低（必须重绘所有内容）。现代浏览器通常先记录这些绘制指令，再通过合成步骤组装最终图像，尤其是在使用 GPU 加速时。

**Layering and compositing**: Compositing is an optimization where the page is split into several layers that can be handled independently. For example, a positioned element with a CSS transform or an animation might get its own layer. Layers are like separate "scratch canvases" - the browser can rasterize (draw) each layer separately, and then the compositor can blend them together on the screen, often using the GPU.分层与合成：合成是一种优化技术，将页面拆分为多个可独立处理的图层。例如，带有 CSS 变换或动画的定位元素可能会获得独立图层。这些图层如同独立的"草稿画布"——浏览器可分别对每个图层进行光栅化（绘制），随后合成器（通常借助 GPU）将这些图层在屏幕上混合呈现。

In Chromium's pipeline, after paint records are generated, there's a step to build the layer tree (this corresponds to which elements are on which layer). Some layers are created automatically (e.g. a video element, or a canvas, or elements with certain CSS will be promoted to layers), and developers can hint by using will-change or CSS properties like transform to get a layer. The reason layers are helpful is that movement or opacity changes on a layer can be composited (i.e. just that layer re-rendered or moved) without re-painting the whole page. Too many layers, however, can be memory-heavy and add overhead, so browsers choose carefully.在 Chromium 的渲染管线中，生成绘制记录后，下一步是构建图层树（这对应哪些元素位于哪个图层）。某些图层会自动创建（例如视频元素、画布或具有特定 CSS 属性的元素会被提升为图层），开发者也可以通过使用\`will-change\`或\`transform\`等 CSS 属性来提示浏览器创建图层。图层之所以有用，是因为图层上的移动或透明度变化可以通过合成处理（即仅重新渲染或移动该图层），而无需重绘整个页面。然而，过多的图层会占用大量内存并增加开销，因此浏览器会谨慎选择。

After determining layers, Chrome's main thread hands off to the compositor thread. The compositor thread runs in the renderer process but separate from the main thread (so it can keep working even if the main JS thread is busy, which is great for smooth scrolling and animations). The compositor thread's job is to take the layers, rasterize them (convert the drawings into actual pixel bitmaps), and compose them into frames.确定图层后，Chrome 的主线程会将任务移交给合成器线程。合成器线程在渲染进程中运行，但与主线程分离（因此即使主 JS 线程繁忙，它也能继续工作，这对实现流畅滚动和动画效果非常有利）。合成器线程的职责是接收图层、对其进行光栅化处理（将绘制内容转换为实际像素位图），并将这些图层合成为帧画面。

**Rasterization with GPU assistance**: Raster work can also be distributed. In Chrome, the compositor thread breaks layers into smaller tiles (think 256x256 or 512x512 pixel chunks, which are often larger when GPU raster is on, almost always). It then dispatches these to several raster worker threads (which may even run across multiple CPU cores) for concurrent rasterization. Each raster worker takes a tile - essentially a list of drawing commands for that region of a layer - and produces a bitmap (pixel data). Importantly, Skia (Chrome's graphics library) can use the CPU or GPU to rasterize; in Chrome's case, these raster threads typically use CPU to render the pixels and then upload them to GPU memory. Firefox's newer WebRender takes a different approach we'll mention later. The rasterized tiles are stored in GPU memory as textures. Once all needed tiles are drawn, the compositor thread has essentially a set of textured layers ready.借助 GPU 加速的光栅化：光栅化工作同样可以分布式处理。在 Chrome 中，合成线程会将图层分割成更小的图块（通常为 256x256 或 512x512 像素的区块，启用 GPU 光栅化时这些区块往往更大）。随后将这些图块分派给多个光栅化工作线程（这些线程甚至可能跨多个 CPU 核心运行）进行并行光栅化处理。每个光栅化线程处理一个图块——本质上是该图层区域对应的绘制指令列表——并生成位图（像素数据）。值得注意的是，Skia（Chrome 的图形库）既可使用 CPU 也可使用 GPU 进行光栅化；在 Chrome 的实际应用中，这些光栅化线程通常先用 CPU 渲染像素，再将其上传至 GPU 内存。Firefox 较新的 WebRender 则采用了不同的方案，我们稍后会提及。光栅化后的图块以纹理形式存储在 GPU 内存中。当所有需要的图块绘制完成后，合成线程便获得了一组可供使用的纹理化图层。

The compositor then assembles a compositor frame - basically a message to the browser process that includes all the quads (tiles of layers) that make up the screen, their positions, etc. This compositor frame is submitted via IPC back to the browser process, where ultimately the browser's GPU process (a separate process in Chrome for accessing GPU) will take these and display them. The browser process's own UI (like the tab bar) is also drawn via compositor frames, and they all get mixed in the final step. The GPU process receives the frames, and uses the GPU (via OpenGL/DirectX/Metal etc.) to composite them - basically drawing each texture at the right place on screen, applying transforms, etc. very fast. The result is the final image you see displayed.合成器随后组装出一个合成器帧——这本质上是一条发送给浏览器进程的消息，其中包含构成屏幕的所有四边形（图层瓦片）及其位置等信息。该合成器帧通过进程间通信提交回浏览器进程，最终由浏览器的 GPU 进程（Chrome 中用于访问 GPU 的独立进程）接收并显示。浏览器进程自身的界面（如标签栏）也通过合成器帧绘制，所有内容在最后阶段混合。GPU 进程接收这些帧后，利用 GPU（通过 OpenGL/DirectX/Metal 等）进行合成——快速将每个纹理绘制到屏幕正确位置、应用变换等操作，最终形成你看到的显示画面。

The advantage of this pipeline is apparent when you scroll or animate. For example, scrolling a page mostly just changes the viewport on a larger page texture. The compositor can just shift the layer positions and ask the GPU to redraw the new portion coming into view, without the main thread having to repaint everything. If an animation is just a transform (say moving an element that is its own layer), the compositor thread can update that element's position each frame and produce new frames without involving the main thread or re-running style and layout. This is why animations that are "compositing-only" (changing transform or opacity, which don't trigger layout) are recommended for better performance - they can run at 60 FPS smoothly even if the main thread is busy. In contrast, animating something like height or background-color might force re-layout or re-paint each frame, which janks if the main thread can't keep up.此管道的优势在滚动或动画时尤为明显。例如，滚动页面时，主要是在较大页面纹理上改变视口位置。合成器只需调整图层位置，并让 GPU 重新绘制进入视野的新区域，而无需主线程重新绘制所有内容。如果动画仅涉及变换（比如移动一个独立图层的元素），合成线程可以每帧更新该元素的位置并生成新帧，无需主线程参与或重新执行样式与布局计算。这就是为什么推荐使用"仅合成"动画（改变 transform 或 opacity，这些不会触发布局）以获得更佳性能——即使主线程繁忙，它们也能以 60 FPS 流畅运行。相比之下，对高度或背景色等属性进行动画处理，可能会强制每帧重新布局或重绘，若主线程无法跟上节奏，就会导致卡顿。

To put it succinctly, Chrome's rendering pipeline is: DOM → style → layout → paint (record display items) → layerize → raster (tiles) → composite (GPU). Firefox's pipeline is conceptually similar up to the display list stage, but with WebRender it skips explicit layer construction and instead sends a display list to the GPU process, which then handles almost all drawing using GPU shaders (more on this in the comparison section). WebKit (Safari) also uses a multi-threaded compositor and GPU rendering via "CALayers" on macOS. All modern engines thus take advantage of GPUs for rendering, especially for compositing and rasterizing graphics-intensive parts, to achieve high frame rates and offload work from the CPU.简而言之，Chrome 的渲染管线是：DOM → 样式 → 布局 → 绘制（记录显示项）→ 分层 → 光栅化（瓦片）→ 合成（GPU）。Firefox 的管线在显示列表阶段之前概念上类似，但使用 WebRender 后跳过了显式图层构建，而是将显示列表发送到 GPU 进程，随后几乎全部通过 GPU 着色器完成绘制（更多细节见对比部分）。WebKit（Safari）在 macOS 上也采用多线程合成器，并通过"CALayers"实现 GPU 渲染。因此，所有现代引擎都利用 GPU 进行渲染，特别是合成和光栅化图形密集型部分，以实现高帧率并减轻 CPU 负担。

Before moving on, let's discuss the GPU's role in more detail. In Chromium, the GPU process is a separate process whose job is to interface with the graphics hardware. It receives drawing commands (mostly high-level, like "draw these textures at these coords") from all renderer compositors and also the browser UI. It then translates that into actual GPU API calls. By isolating it in a process, a buggy GPU driver that crashes won't take down the whole browser - only the GPU process, which can be restarted. Also, it provides a sandbox boundary (since GPUs process potentially untrusted content like canvas drawing, WebGL, etc. there have been security bugs in drivers - running them out-of-process mitigates risk).在继续之前，我们先详细讨论一下 GPU 的作用。在 Chromium 中，GPU 进程是一个独立的进程，其职责是与图形硬件进行交互。它接收来自所有渲染合成器以及浏览器界面的绘图指令（主要是高级指令，例如"在指定坐标绘制这些纹理"），然后将这些指令转换为实际的 GPU API 调用。通过将其隔离在独立进程中，即使有问题的 GPU 驱动程序崩溃，也不会导致整个浏览器崩溃——只会影响 GPU 进程，而该进程可以重新启动。此外，这还提供了一个沙箱边界（由于 GPU 会处理可能不受信任的内容，如画布绘图、WebGL 等，驱动程序中曾存在安全漏洞——通过进程外运行可以降低风险）。

The result of the compositing is finally sent to the display (the OS window or context the browser is running in). For each animation frame (target 60fps or 16.7ms per frame for smooth results), the compositor aims to produce a frame. If the main thread is busy (say JavaScript took a long time), the compositor might skip frames or can't update, leading to visible jank. Developer tools can show dropped frames in the performance timeline. Techniques like requestAnimationFrame align JS updates to frame boundaries to help with smooth rendering.合成结果最终被发送到显示器（即浏览器运行的操作系统窗口或上下文）。对于每个动画帧（目标为 60fps，即每帧 16.7 毫秒以实现流畅效果），合成器会尝试生成一帧。如果主线程繁忙（例如 JavaScript 执行耗时较长），合成器可能会跳过帧或无法更新，从而导致明显的卡顿。开发者工具可以在性能时间线中显示丢帧情况。像\`requestAnimationFrame\`这样的技术可以将 JavaScript 更新与帧边界对齐，有助于实现流畅渲染。

In summary, the browser's rendering engine carefully breaks down the page content and styles into a set of geometry (layout) and drawing instructions, then uses layers and GPU compositing to efficiently turn that into the pixels you see. This complex pipeline is what enables the rich graphics and animations on the web to run at interactive frame rates. Next, we will peek into the JavaScript engine to understand how the browser executes scripts (which we've so far treated as a black box).总而言之，浏览器的渲染引擎会将页面内容和样式细致地分解为一组几何信息（布局）和绘制指令，然后利用图层和 GPU 合成，高效地将其转化为你所看到的像素。正是这一复杂的流水线，使得网页上的丰富图形和动画能够以交互式帧率运行。接下来，我们将深入 JavaScript 引擎，了解浏览器如何执行脚本（到目前为止，我们一直将其视为一个黑盒）。

## Inside the JavaScript Engine (V8)深入 JavaScript 引擎（V8）

JavaScript drives the interactive behavior of web pages. In Chromium browsers, the V8 engine executes JavaScript (and WebAssembly). Understanding V8's workings can help developers write performant JS. While an exhaustive deep-dive would be book-length, we'll focus on the key stages of the JS execution pipeline: parsing/compiling the code, executing it, and managing memory (garbage collection). We'll also note how V8 handles modern features like Just-In-Time (JIT) compilation tiers and ES modules.JavaScript 驱动着网页的交互行为。在 Chromium 浏览器中，V8 引擎负责执行 JavaScript（及 WebAssembly）。理解 V8 的工作原理有助于开发者编写高性能的 JS 代码。虽然深入剖析足以成书，但我们将聚焦 JS 执行管线的关键阶段：代码解析/编译、执行过程以及内存管理（垃圾回收）。我们还将探讨 V8 如何处理现代特性，例如即时编译（JIT）分层机制和 ES 模块。

**Background compilation**: Starting with Chrome 66, V8 compiles JavaScript source code on a background thread, reducing the amount of time spent compiling on the main thread by between 5% to 20% on typical websites. Since version 41, Chrome has supported parsing of JavaScript source files on a background thread via V8's StreamedSource API. V8 can start parsing JavaScript source code as soon as the first chunk is downloaded from the network and continue parsing in parallel while streaming the file. Almost all script compilation occurs on background threads, with only short AST internalization and bytecode finalization steps happening on the main thread just before script execution. Currently, top-level script code and immediately invoked function expressions are compiled on background threads, while inner functions are still compiled lazily on the main thread when first executed.后台编译：从 Chrome 66 开始，V8 在后台线程上编译 JavaScript 源代码，使典型网站的主线程编译时间减少 5%至 20%。自 Chrome 41 起，Chrome 已支持通过 V8 的 StreamedSource API 在后台线程上解析 JavaScript 源文件。V8 可在从网络下载首个数据块后立即开始解析 JavaScript 源代码，并在流式传输文件的同时并行解析。几乎所有脚本编译都在后台线程上完成，仅在脚本执行前，主线程上会进行短暂的 AST 内部化和字节码最终化步骤。目前，顶层脚本代码和立即调用函数表达式在后台线程上编译，而内部函数仍会在首次执行时于主线程上延迟编译。

**Parsing and bytecode**: When a \<script> is encountered (either during HTML parse or loaded later), V8 first parses the JavaScript source code. This produces an Abstract Syntax Tree (AST) representation of the code. The preparser is a copy of the parser that does the bare minimum needed to skip over functions. It verifies that functions are syntactically valid and produces all information needed for outer functions to be compiled correctly. When a preparsed function is later called, it is fully parsed and compiled on-demand.解析与字节码：当遇到 \`\<script>\` 标签时（无论是在 HTML 解析过程中还是稍后加载），V8 首先会解析 JavaScript 源代码。这一过程会生成代码的抽象语法树（AST）表示。预解析器是解析器的一个副本，仅执行跳过函数所需的最基本操作。它会验证函数的语法正确性，并生成外部函数正确编译所需的所有信息。当预解析的函数后续被调用时，才会按需进行完整解析和编译。

Rather than interpreting directly from the AST, V8 uses a bytecode interpreter called Ignition (introduced in 2016). Ignition compiles the JavaScript into a compact bytecode format, which is essentially a sequence of instructions for a virtual machine. This initial compilation is quite fast and the bytecode is fairly low-level (Ignition is a register-based VM). The goal is to start executing the code quickly with minimal upfront cost (important for page load times).V8 并非直接从 AST 进行解释，而是使用名为 Ignition（2016 年引入）的字节码解释器。Ignition 将 JavaScript 编译成紧凑的字节码格式，这本质上是虚拟机的一系列指令。这种初始编译速度相当快，且字节码处于较低层级（Ignition 是一个基于寄存器的虚拟机）。其目标是以前期最小成本快速开始执行代码（这对页面加载时间至关重要）。

**AST internalization process**: AST internalization involves allocating literal objects (strings, numbers, object-literal boilerplate) on the V8 heap for use by generated bytecode. To enable background compilation, this process was moved later in the compilation pipeline, after bytecode compilation, requiring modifications to access raw literal values embedded in the AST instead of internalized on-heap values.AST 内部化过程：AST 内部化涉及在 V8 堆上分配字面量对象（字符串、数字、对象字面量模板），以供生成的字节码使用。为支持后台编译，该过程被移至编译管线的更后阶段（字节码编译之后），这需要修改代码以访问嵌入在 AST 中的原始字面量值，而非已内部化的堆上值。

**Explicit Compile Hints**: V8 has introduced a new feature called "[Explicit Compile Hints](https://v8.dev/blog/explicit-compile-hints)" which allows developers to instruct V8 to parse and compile code immediately on load through eager compilation. Files with this hint are compiled on background threads, whereas deferred compilation happens on the main thread. Experiments with popular web pages showed performance improvements in 17 out of 20 cases, with an average 630ms reduction in foreground parse and compile times. Developers can add explicit compile hints to JavaScript files using special comments to enable eager compilation on background threads for critical code paths.显式编译提示：V8 引入了一项名为"显式编译提示"的新功能，允许开发者通过预编译方式指示 V8 在加载时立即解析并编译代码。带有此提示的文件将在后台线程中编译，而延迟编译则会在主线程进行。对热门网页的测试显示，20 个案例中有 17 个获得性能提升，前台解析与编译时间平均减少 630 毫秒。开发者可通过特殊注释为 JavaScript 文件添加显式编译提示，使关键代码路径在后台线程实现预编译。

**Scanner and parser optimizations**: V8's scanner has been significantly optimized, resulting in improvements across the board: single token scanning improved by roughly 1.4×, string scanning by 1.3×, multiline comment scanning by 2.1×, and identifier scanning by 1.2-1.5× depending on identifier length.扫描器与解析器优化：V8 的扫描器经过显著优化，各项性能全面提升：单令牌扫描速度提升约 1.4 倍，字符串扫描提升 1.3 倍，多行注释扫描提升 2.1 倍，标识符扫描根据长度不同提升 1.2 至 1.5 倍。

When the script runs, Ignition interprets the bytecode, executing the program. Interpretation is generally slower than optimized machine code, but it allows the engine to start running and also collect profiling information about the code's behavior. As the code runs, V8 gathers data on how it's being used: types of variables, which functions are called frequently, etc. This information will be used to make the code run faster in subsequent steps.当脚本运行时，Ignition 会解释字节码并执行程序。解释执行通常比优化后的机器码慢，但它能让引擎快速启动运行，同时收集代码运行时的性能分析信息。随着代码的执行，V8 会持续收集代码的使用数据：变量类型、频繁调用的函数等。这些信息将在后续步骤中用于加速代码运行。

**JIT Compilation TiersJIT 编译层级**

V8 doesn't stop at interpretation. It employs multiple tiers of Just-In-Time compilers to accelerate hot code. The idea is to spend more compilation effort on code that runs a lot, to make it faster, while not wasting time optimizing code that runs only once.V8 并不止步于解释执行。它采用多级即时编译器来加速热点代码。其核心思路是：对频繁执行的代码投入更多编译优化资源以提升其运行速度，同时避免对仅执行一次的代码浪费优化时间。

1. **Ignition** (interpreting the bytecode).Ignition（解释执行字节码）。
2. **Sparkplug**: V8's baseline JIT called Sparkplug (launched around 2021). Sparkplug takes the bytecode and compiles it to machine code quickly, without heavy optimizations. This yields native code that is faster than interpretation but Sparkplug doesn't do deep analysis - it's meant to be almost as quick as the interpreter to start, but produce code that runs a bit faster.Sparkplug：V8 的基线 JIT 编译器称为 Sparkplug（大约在 2021 年推出）。Sparkplug 将字节码快速编译为机器码，不进行重度优化。这样生成的本地代码比解释执行更快，但 Sparkplug 不进行深度分析——它的设计目标是启动速度几乎与解释器一样快，同时生成的代码运行速度稍快一些。
3. **Maglev**: In 2023, V8 introduced Maglev, a mid-tier optimizing compiler that is now actively deployed. Maglev generates code nearly 20 times slower than Sparkplug but 10 to 100 times faster than TurboFan, effectively bridging the gap for functions that are moderately hot but not hot enough for TurboFan optimization. Maglev comes into play for functions that are somewhat hot but not hot enough for TurboFan, or when TurboFan's compilation would be too costly. As of Chrome M117, Maglev can handle many cases, resulting in faster startup for web apps that spend time in "warm" code (not cold, not super hot) by bridging the gap between baseline and highest-tier JIT.磁悬浮：2023 年，V8 引入了 Maglev 这一中层优化编译器，目前已投入实际应用。Maglev 生成代码的速度比 Sparkplug 慢近 20 倍，但比 TurboFan 快 10 到 100 倍，有效填补了那些热度中等但尚未达到 TurboFan 优化门槛的函数之间的性能鸿沟。当函数处于"较热"状态但不足以触发 TurboFan 优化，或 TurboFan 编译成本过高时，Maglev 便会发挥作用。自 Chrome M117 起，Maglev 已能处理多种场景，通过弥合基线 JIT 与最高层级 JIT 之间的差距，使那些需要处理"温热"代码（既非冷代码也非超热代码）的 Web 应用启动速度显著提升。
4. **TurboFan**: As functions or loops get executed many times, V8 will engage its most powerful optimizing compiler. TurboFan takes the code and uses the collected type feedback to generate highly optimized machine code, applying advanced optimizations (inlining functions, eliding bounds checks, etc.). Note: as of 2025, V8 has been incrementally replacing TurboFan's internal "Sea of Nodes" intermediate representation with a CFG-based IR called Turboshaft. The entire JavaScript backend of TurboFan now uses Turboshaft, and a further project (Turbolev) is underway to use Maglev's IR as the frontend, replacing TurboFan's front-end entirely. This optimized code can run much faster if the assumptions hold.TurboFan：当函数或循环被多次执行时，V8 会启用其最强大的优化编译器。TurboFan 接收代码，利用收集到的类型反馈生成高度优化的机器码，并应用高级优化（如函数内联、边界检查消除等）。注意：截至 2025 年，V8 已逐步将 TurboFan 内部的"节点之海"中间表示替换为基于 CFG 的 IR（称为 Turboshaft）。TurboFan 的整个 JavaScript 后端现已采用 Turboshaft，同时正在推进另一项目（Turbolev），计划使用 Maglev 的 IR 作为前端，完全取代 TurboFan 的前端。若假设条件成立，这种优化后的代码运行速度将大幅提升。

So V8 now effectively has four execution tiers: Ignition interpreter, Sparkplug baseline JIT, Maglev optimizing JIT, and TurboFan optimizing JIT (whose backend is progressively being replaced by Turboshaft). This is analogous to how Java's HotSpot VM has multiple JIT levels (C1 and C2). The engine can dynamically decide which functions to optimize and when, based on execution profiles. If a function suddenly is called a million times, it will likely end up TurboFan-optimized for maximum speed.因此，V8 现在实际上拥有四个执行层级：Ignition 解释器、Sparkplug 基线 JIT、Maglev 优化 JIT 以及 TurboFan 优化 JIT（其后端正逐步被 Turboshaft 取代）。这与 Java 的 HotSpot 虚拟机拥有多个 JIT 层级（C1 和 C2）类似。引擎可以根据执行配置文件动态决定优化哪些函数以及何时优化。如果某个函数突然被调用数百万次，它很可能会被 TurboFan 优化以达到最高速度。

Intel has also developed [Profile-Guided Tiering](https://community.intel.com/t5/Blogs/Tech-Innovation/Client/Profile-Guided-Tiering-in-the-V8-JavaScript-Engine/post/1679340) that enhances V8's efficiency, leading to approximately 5% improvement on Speedometer 3 benchmarks. Recent V8 updates include static roots optimization, which allows accurate prediction of memory addresses at compile time for commonly used objects, significantly improving access speed.英特尔还开发了配置文件引导的分层技术，提升了 V8 的效率，使 Speedometer 3 基准测试性能提升约 5%。最近的 V8 更新包括静态根优化，该优化允许在编译时准确预测常用对象的内存地址，从而显著提高访问速度。

One challenge with JIT optimization is that JavaScript is dynamically typed. V8 might optimize code under certain assumptions (e.g. this variable is always an integer). If a later call violates those assumptions (say the variable becomes a string), the optimized code is invalid. V8 then performs a deoptimization: it falls back to a less optimized version (or re-generates code with new assumptions). This mechanism relies on "inline caches" and type feedback to quickly adapt. The existence of deopt means sometimes peak performance isn't sustained if your code has unpredictable types, but generally V8 tries to handle typical patterns (like a function consistently being passed the same type of object).JIT 优化面临的一个挑战是 JavaScript 的动态类型特性。V8 可能会基于某些假设来优化代码（例如：这个变量始终是整数类型）。如果后续调用违反了这些假设（比如变量变成了字符串类型），优化后的代码就会失效。此时 V8 会执行去优化操作：回退到未优化的版本（或根据新假设重新生成代码）。这种机制依赖于"内联缓存"和类型反馈来快速适应变化。去优化的存在意味着，如果代码包含不可预测的类型，峰值性能可能无法持续，但 V8 通常会尽力处理典型模式（比如某个函数始终接收相同类型的对象）。

**Bytecode Flushing and Memory Management字节码刷新与内存管理**

V8 implements bytecode flushing where if a function remains unused after multiple garbage collections, its bytecode will be reclaimed. When executed again, the parser uses previously stored results to regenerate the bytecode more quickly. This mechanism is crucial for memory management but can lead to parsing inconsistencies in edge cases.V8 实现了字节码刷新机制：当某个函数在多次垃圾回收后仍未被使用，其字节码将被回收。当该函数再次执行时，解析器会利用先前存储的结果更快地重新生成字节码。这一机制对内存管理至关重要，但在极端情况下可能导致解析不一致。

**Memory Management (Garbage Collection)**: V8 automatically manages memory for JS objects using a garbage collector. Over the years, V8's GC has evolved into what's known as the Orinoco GC, which is a generational, incremental, and concurrent garbage collector. Key points:内存管理（垃圾回收）：V8 通过垃圾回收器自动管理 JavaScript 对象的内存。多年来，V8 的垃圾回收器已演进为被称为 Orinoco 的垃圾回收器，这是一种分代式、增量式且并发的垃圾回收器。关键要点如下：

- **Generational**: V8 segregates objects by age. New objects are allocated in the young generation (or "nursery"). These are collected frequently with a very fast scavenging algorithm (copying live objects to a new space and reclaiming the rest). Objects that survive enough cycles get promoted to the old generation.分代式：V8 按对象存活时间进行隔离。新对象被分配在新生代（或称"nursery"区域）。这些对象通过极快的清除算法（将存活对象复制到新空间并回收其余部分）进行频繁回收。经过足够多次回收周期仍存活的对象会被晋升至老年代。
- **Mark-and-sweep/compact**: For the old generation, V8 uses a mark-and-sweep collector with compaction. This means it will occasionally stop the world (stop JS execution briefly), mark all reachable objects (tracing from roots like the global object), then sweep to reclaim memory from unreferenced objects. It may also compact memory (moving objects to reduce fragmentation). However, Orinoco has made much of the marking concurrent - it can do a lot of the marking on a background thread while JS is still running, to minimize pause times.标记-清除/压缩：对于老生代，V8 采用带压缩功能的标记-清除回收器。这意味着它会偶尔暂停全局（短暂停止 JS 执行），标记所有可达对象（从全局对象等根节点开始追踪），然后清除以回收未被引用对象的内存。它还可能进行内存压缩（移动对象以减少碎片化）。不过，Orinoco 已经实现了大部分标记操作的并发执行——它可以在 JS 仍在运行时，在后台线程完成大量标记工作，从而最大限度减少暂停时间。
- **Incremental GC**: V8 performs garbage collection in small slices rather than one big pause when possible. This incremental approach spreads work out to avoid jank. For example, it can interleave a bit of marking work between script executions, using idle time.增量式垃圾回收：V8 在可能的情况下会以小片段而非一次性大停顿的方式执行垃圾回收。这种增量方法将工作分散开来，以避免卡顿。例如，它可以在脚本执行之间穿插少量标记工作，利用空闲时间。
- **Parallel GC**: On multi-core machines, V8 can perform parts of GC (like marking or sweeping) in parallel threads as well.并行垃圾回收：在多核机器上，V8 可以在并行线程中执行部分垃圾回收操作（如标记或清除）。

The net effect is that the V8 team has managed to drastically reduce GC pause times over the years, making garbage collection mostly unnoticeable even in large applications. Minor GCs (new object scavenge) usually happen very fast. Major GCs (old gen) are rarer and mostly concurrent now. If you open Chrome's Task Manager or DevTools Memory panel, you might see V8's heap broken into "Young space" and "Old space" reflecting this generational design.最终结果是，V8 团队多年来成功大幅减少了垃圾回收的暂停时间，使得即使在大型应用中，垃圾回收也几乎不被察觉。新生代垃圾回收（新对象清理）通常执行得非常快。老年代垃圾回收（旧对象清理）频率较低，且现在大多采用并发方式。如果你打开 Chrome 的任务管理器或 DevTools 内存面板，可能会看到 V8 的堆内存被划分为"新生代空间"和"老年代空间"，这正是这种分代设计的体现。

For developers, this means manual memory management isn't needed, but you should still be mindful: e.g. avoid creating tons of short-lived objects in tight loops (though V8 is quite good at handling short-lived objects) and be aware that holding onto large data structures will keep them around in memory. Tools like DevTools can force a garbage collection or record memory profiles to see what is using memory.对于开发者而言，这意味着无需手动管理内存，但仍需注意：例如，避免在紧密循环中创建大量短生命周期对象（尽管 V8 处理短生命周期对象的能力很强），同时要意识到持有大型数据结构会导致它们持续占用内存。借助 DevTools 等工具，可以强制执行垃圾回收或记录内存快照，从而分析内存使用情况。

**V8 and Web APIs**: It's worth mentioning that V8 covers the core JavaScript language and runtime (execution, standard JS objects, etc.), but many "browser APIs" (like DOM methods, alert(), network XHR/fetch, etc.) are not part of V8 itself. Those are provided by the browser and are exposed to JS via bindings. For instance, when you call document.querySelector, under the hood it enters the engine's binding to the C++ DOM implementation. V8 handles calling into C++ and getting results back, and there is a lot of machinery to make this boundary fast (Chrome uses an IDL to generate efficient bindings).V8 与 Web API：需要说明的是，V8 涵盖了核心 JavaScript 语言及其运行时（执行机制、标准 JS 对象等），但许多"浏览器 API"（如 DOM 方法、alert()、网络 XHR/fetch 等）并不属于 V8 本身。这些功能由浏览器提供，并通过绑定机制暴露给 JavaScript。例如，当你调用 document.querySelector 时，底层会进入引擎与 C++ DOM 实现的绑定层。V8 负责调用 C++代码并获取返回结果，其间存在大量优化机制来提升跨语言边界的执行效率（Chrome 使用 IDL 生成高效的绑定代码）。

Having covered how the browser fetches resources, parses HTML/CSS, computes layout, paints with the GPU, and runs JS, we now have a picture of the entire process of loading and rendering a page. But there's more to explore: how ES modules are handled (since modules involve their own loading mechanism), how the browser's multi-process architecture is organized, and how security features like sandboxing and site isolation work.在了解了浏览器如何获取资源、解析 HTML/CSS、计算布局、通过 GPU 绘制以及运行 JS 之后，我们现在对页面加载和渲染的完整过程有了清晰的认识。但还有更多值得探索的内容：ES 模块的处理方式（因为模块涉及自身的加载机制）、浏览器多进程架构的组织形式，以及沙箱隔离和站点隔离等安全特性的工作原理。

## Module Loading and Import Maps模块加载与导入映射

[JavaScript modules](https://v8.dev/features/modules) (ES6 modules) introduce a different loading and execution model compared to classic \<script> tags. Instead of a big script file that might create globals, modules are files that explicitly import/export values. Let's see how browsers (and specifically V8 in Chrome) load modules and how features like dynamic import() and import maps come into play.JavaScript 模块（ES6 模块）引入了一种与经典\<script>标签不同的加载和执行模型。模块不再是可能创建全局变量的庞大脚本文件，而是显式导入/导出值的文件。让我们看看浏览器（特别是 Chrome 中的 V8 引擎）如何加载模块，以及动态 import()和导入映射等功能如何发挥作用。

**Static module imports**: When the browser encounters a \<script type="module" src="main.js">, it treats main.js as a module entry point. The loading process works as follows: the browser will fetch main.js, then parse it as an ES module. During parsing, it will find any import statements (e.g. import { foo } from './utils.js';). Rather than executing code immediately, the browser constructs a module dependency graph. It will initiate fetching of any imported modules (utils.js in this case), and recursively, each of those modules is parsed for their imports, fetched, and so on. This happens asynchronously. Only once the entire graph of modules is fetched and parsed can the browser evaluate the modules. Module scripts are deferred by nature - the browser doesn't execute the module code until all dependencies are ready. Then it executes them in dependency order (ensuring that if module A imports B, B runs first).静态模块导入：当浏览器遇到 \`\<script type="module" src="main.js">\` 时，会将 main.js 视为模块入口点。加载过程如下：浏览器会获取 main.js，然后将其解析为 ES 模块。在解析过程中，它会发现所有 import 语句（例如 \`import { foo } from './utils.js';\`）。浏览器不会立即执行代码，而是构建一个模块依赖关系图。它会开始获取所有导入的模块（本例中的 utils.js），并递归地对每个模块进行解析、获取其导入项，以此类推。这个过程是异步进行的。只有当整个模块依赖图被完全获取并解析后，浏览器才能对模块进行评估。模块脚本本质上是延迟执行的——浏览器会等到所有依赖项准备就绪后才执行模块代码。然后它会按照依赖顺序执行（确保如果模块 A 导入了模块 B，则 B 先运行）。

This static import process is why ES modules can't be loaded from file:// in some cases unless allowed, and why they require CORS by default for cross-origin scripts - the browser is actively linking and loading multiple files, not just dropping a \<script> into the page.这种静态导入过程解释了为什么 ES 模块在某些情况下无法从 file://加载（除非被允许），以及为什么它们默认要求跨域脚本使用 CORS——因为浏览器正在主动链接和加载多个文件，而不仅仅是向页面中插入一个\<script>标签。

**Dynamic import()**: In addition to static import statements, ES2020 introduced import(moduleSpecifier) as an expression. This allows code to load a module on the fly (returning a promise that resolves to the module exports). For example, you might do const module = await import('./analytics.js') in response to a user action, thereby code-splitting your application. Under the hood, import() triggers the browser to fetch the requested module (and its dependencies, if not already loaded), then instantiate and execute it, and resolve the promise with the module namespace object. V8 and the browser coordinate here: the browser's module loader handles fetching and parsing, V8 handles the compilation and execution once ready. Dynamic import is powerful because it can be used in non-module scripts too (e.g. an inline script can dynamically import a module). It essentially gives the developer control to load JS on demand. The difference from a static import is that static imports are resolved ahead of time (before any module code runs, the entire graph is loaded), whereas dynamic import behaves more like loading a new script at runtime (except with module semantics and promises).动态导入\`import()\`：除了静态导入语句外，ES2020 还引入了\`import(moduleSpecifier)\`表达式。这使得代码能够动态加载模块（返回一个解析为模块导出的 Promise）。例如，你可以根据用户操作执行\`const module = await import('./analytics.js')\`，从而实现应用的代码分割。在底层实现中，\`import()\`会触发浏览器获取请求的模块（及其尚未加载的依赖项），然后实例化并执行该模块，最后用模块命名空间对象解析 Promise。V8 引擎与浏览器在此协同工作：浏览器的模块加载器负责获取和解析，V8 则负责在准备就绪后编译和执行。动态导入的强大之处在于它也能在非模块脚本中使用（例如内联脚本可以动态导入模块）。这本质上赋予了开发者按需加载 JavaScript 的控制权。与静态导入的区别在于：静态导入会提前解析（在任何模块代码运行前，整个依赖图就已加载完毕），而动态导入更像是在运行时加载新脚本（但保留模块语义和 Promise 特性）。

**Import maps**: One challenge with ES modules in the browser was the module specifiers. In Node or bundlers, you often import by package name (e.g. import { compile } from 'react'). On the web, without a bundler, 'react' is not a valid URL - the browser would treat it as a relative path (which would fail). This is where Import Maps come in. An import map is a JSON configuration that tells the browser how to resolve module specifiers to real URLs. It's provided via a \<script type="importmap"> tag in HTML. For example, an import map might say that the specifier "react" maps to "[https://cdn.example.com/react@19.0.0/index.js](https://cdn.example.com/react@19.0.0/index.js)" (some full URL to the actual script). Then, when any module does import 'react', the browser uses the map to find the URL and loads that. Essentially, import maps allow "bare" specifiers (like package names) to work on the web by mapping them to CDN URLs or local paths.导入映射：浏览器中 ES 模块面临的一个挑战是模块标识符。在 Node 或打包工具中，我们常通过包名进行导入（例如 \`import { compile } from 'react'\`）。但在没有打包工具的网页环境中，'react' 并非有效 URL——浏览器会将其视为相对路径（导致加载失败）。这正是导入映射的用武之地。导入映射是一种 JSON 配置，用于告知浏览器如何将模块标识符解析为真实 URL。它通过 HTML 中的 \`\<script type="importmap">\` 标签提供。例如，导入映射可指定标识符 "react" 映射至 "https://cdn.example.com/react@19.0.0/index.js"（指向实际脚本的完整 URL）。此后，当任何模块执行 \`import 'react'\` 时，浏览器便会根据映射查找对应 URL 并加载该模块。本质上，导入映射通过将"裸"标识符（如包名）映射至 CDN 地址或本地路径，使其能在网页环境中正常工作。

Import maps have been a game-changer for unbundled development. Since 2023, import maps are supported in all major browsers (Chrome 89+, Firefox 108+, Safari 16.4+ - all three engines). They are especially useful for local development or simple apps where you want to use modules without a build step. For production, large apps often still bundle for performance (to reduce the number of requests), but as browsers and HTTP/2/3 improve, serving many small modules becomes more viable.导入映射表已成为无打包开发模式的变革者。自 2023 年起，所有主流浏览器（Chrome 89+、Firefox 108+、Safari 16.4+——三大引擎均已支持）均支持导入映射表。对于希望在不使用构建步骤的情况下使用模块的本地开发或简单应用而言，该功能尤为实用。在生产环境中，大型应用通常仍会进行打包以提升性能（减少请求数量），但随着浏览器及 HTTP/2/3 协议的持续优化，直接提供大量小型模块的方案正变得愈发可行。

The module loader in the browser thus consists of: a module map (tracking what's been loaded), possibly an import map (for custom resolution), and the fetching/parsing logic. Once fetched and compiled, module code executes in strict mode and with its own top-level scope (no leaking to window unless explicitly attached). The exports are cached so if another module imports the same module later, it doesn't re-run it (it reuses the already evaluated module record).浏览器中的模块加载器因此包含：一个模块映射表（追踪已加载的模块）、可能存在的导入映射表（用于自定义解析），以及获取/解析逻辑。模块在获取并编译后，会以严格模式执行，并拥有自己的顶级作用域（除非显式挂载，否则不会泄漏到 window 对象）。导出内容会被缓存，因此如果其他模块稍后导入同一模块，不会重新执行它（而是复用已求值的模块记录）。

One more aspect to mention is that ES modules, unlike scripts, defer execution and also execute in order for a given graph. If main.js imports util.js and util.js imports dep.js, the evaluation order will be: dep.js first, then util.js, then main.js (depth-first, post-order). This deterministic order can avoid the need for things like DOMContentLoaded in some cases, since by the time your main module runs, all its imports are loaded and executed.还需提及的一点是，ES 模块与脚本不同，它会延迟执行，并且对于给定的依赖图按顺序执行。如果 main.js 导入 util.js，而 util.js 又导入 dep.js，那么求值顺序将是：先执行 dep.js，再执行 util.js，最后执行 main.js（深度优先、后序遍历）。这种确定的执行顺序在某些情况下可以避免对 DOMContentLoaded 等事件的依赖，因为当主模块运行时，其所有导入内容都已加载并执行完毕。

From V8's perspective, modules are handled by the same compilation pipeline, but they create separate ModuleRecords. The engine ensures that a module's top-level code only runs once all dependencies are ready. V8 also has to deal with cyclic module imports (which are allowed and can lead to partially initialized exports). The details are per spec - but essentially, the engine will create all module instances, then resolve cycles by giving them placeholders, and then execute in an order that respects dependencies (the spec algorithm is the "DAG" topological sort of the module graph).从 V8 的角度来看，模块由相同的编译管道处理，但会创建独立的 ModuleRecords。引擎确保模块的顶层代码仅在所有依赖项就绪后运行。V8 还需要处理循环模块导入（这是允许的，可能导致部分初始化的导出）。具体细节遵循规范——但本质上，引擎会先创建所有模块实例，然后通过占位符解析循环依赖，最后按照依赖顺序执行（规范算法是模块图的"DAG"拓扑排序）。

In summary, module loading in browsers is a coordinated dance between the network (fetching module files), the module resolver (using import maps or standard URL resolution), and the JS engine (compiling and evaluating modules in the correct order). It's more involved than old \<script> loading, but results in a more modular and maintainable code structure. For developers, the key takeaways are: use modules to organize code, use import maps if you want bare imports, and know that you can dynamically load modules when needed via import(). The browser will handle the heavy lifting of making sure everything executes in the right sequence.总之，浏览器中的模块加载是网络（获取模块文件）、模块解析器（使用导入映射或标准 URL 解析）和 JS 引擎（按正确顺序编译和执行模块）之间的协同配合。这比传统的\<script>加载更复杂，但能实现更模块化、更易维护的代码结构。对开发者而言，核心要点是：使用模块组织代码，需要裸导入时使用导入映射，并了解可通过 import()动态加载模块。浏览器会负责确保所有内容按正确顺序执行。

Now that we've covered how a single page's internals work, let's zoom out and examine the browser architecture that allows multiple pages, tabs, and web apps to all run simultaneously without interfering with each other. This brings us to the multi-process model.了解了单个页面的内部运作机制后，让我们将视野放宽，审视一下浏览器架构是如何让多个页面、标签页和网络应用同时运行且互不干扰的。这就引出了多进程模型。

## Browser Multi-Process Architecture浏览器多进程架构

Modern browsers (Chrome, Firefox, Safari, Edge, etc.) all use a multi-process architecture for stability, security, and performance isolation. Instead of running the entire browser as one giant process (which was how early browsers worked), different aspects of the browser run in different processes. Chrome was a pioneer of this approach in 2008, and others followed suit in various forms. Let's focus on Chromium's architecture and note differences in Firefox and Safari.现代浏览器（Chrome、Firefox、Safari、Edge 等）均采用多进程架构，以实现稳定性、安全性和性能隔离。与早期浏览器将整个浏览器作为一个巨型进程运行的方式不同，浏览器的不同功能模块运行在不同的进程中。Chrome 在 2008 年率先采用此方法，其他浏览器也以不同形式相继效仿。我们重点分析 Chromium 的架构，并指出 Firefox 和 Safari 的差异。

In Chromium (Chrome, Edge, Brave, etc.), there is one **Browser Process** that is central. This browser process is responsible for the UI (the address bar, bookmarks, menus - all the browser chrome) and for coordinating high-level tasks like resource loading and navigation. When you open Chrome and see one entry in your OS task manager, that's the browser process. It's also the parent that spawns other processes.在 Chromium（Chrome、Edge、Brave 等）中，存在一个核心的浏览器进程。该浏览器进程负责用户界面（地址栏、书签、菜单——所有浏览器界面元素），并协调资源加载和导航等高级任务。当你在操作系统任务管理器中看到 Chrome 的一个条目时，那便是浏览器进程。它也是生成其他进程的父进程。

Then, for each tab (and sometimes for each site in a tab), Chrome creates a **Renderer Process**. A renderer process runs the Blink rendering engine and V8 JS engine for the content of that tab. In general, each tab gets at least one renderer process.然后，对于每个标签页（有时是标签页中的每个站点），Chrome 会创建一个渲染器进程。渲染器进程会运行 Blink 渲染引擎和 V8 JS 引擎来处理该标签页的内容。通常情况下，每个标签页至少会分配一个渲染器进程。

![Image](https://pbs.twimg.com/media/HLOM63vbMAAfOhw?format=jpg&name=large)

If you have multiple unrelated sites open, they'll be in separate processes (Site A in one, Site B in another, etc.). Chrome even isolates cross-origin iframes into separate processes (more on that in site isolation). The renderer process is sandboxed and cannot directly access your file system or network arbitrarily - it has to go through the browser process for those privileged operations.如果你同时打开了多个不相关的网站，它们会运行在独立的进程中（例如网站 A 在一个进程，网站 B 在另一个进程等）。Chrome 甚至会将跨源 iframe 隔离到单独的进程中（更多细节请参阅站点隔离机制）。渲染进程被置于沙盒环境中，无法直接随意访问你的文件系统或网络——它必须通过浏览器进程才能执行这些特权操作。

Other key processes in Chrome include:Chrome 中的其他关键进程包括：

- **GPU Process**: a process dedicated to communicating with the GPU (as described earlier). All rendering and compositing requests from renderers go to the GPU process, which actually issues graphics API calls. This process is sandboxed and separate so that a GPU crash doesn't take down renderers.GPU 进程：一个专门用于与 GPU 通信的进程（如前所述）。所有来自渲染器的渲染和合成请求都会发送到 GPU 进程，该进程实际发出图形 API 调用。此进程被沙盒化且独立，因此 GPU 崩溃不会导致渲染器宕机。
- **Network Process**: (In older Chrome versions the network was a thread in browser process, but now it's often a separate process through "servicification"). This process handles network requests, DNS, etc. and can be sandboxed separately.网络进程：（在旧版 Chrome 中，网络是浏览器进程中的一个线程，但现在通过"服务化"通常成为一个独立进程）。该进程处理网络请求、DNS 等任务，并可单独进行沙盒化处理。
- **Utility Processes**: these are for various services (like audio playback, image decoding, etc.) that Chrome may offload.实用进程：这些用于各种服务（如音频播放、图像解码等），Chrome 可能会将这些任务分流处理。
- **Plugin Process**: in the era of Flash and NPAPI plugins, plugins ran in their own process. Flash is deprecated now, so this is less relevant, but the architecture remains ready for plugins to not run in the main browser process.插件进程：在 Flash 和 NPAPI 插件时代，插件运行在独立的进程中。如今 Flash 已被弃用，因此这一机制的重要性有所降低，但架构仍保留着，确保插件不会在主浏览器进程中运行。
- **Extension Processes**: Chrome extensions (which are essentially scripts that can act on web pages or the browser) run in separate processes as well, isolated from websites for security.扩展程序进程：Chrome 扩展程序（本质上是可作用于网页或浏览器的脚本）同样运行在独立进程中，与网站隔离以确保安全。

A simplified view is: one Browser process coordinates multiple Renderer processes (one per tab or per site instance), plus one GPU process and a few others for services. Chrome's task manager (Shift+Esc on Windows or via More Tools > Task Manager) will actually list each process type and its memory usage.简化的视图是：一个浏览器进程协调多个渲染器进程（每个标签页或每个站点实例对应一个），外加一个 GPU 进程和若干其他服务进程。Chrome 的任务管理器（Windows 上按 Shift+Esc，或通过"更多工具">"任务管理器"）会列出每种进程类型及其内存使用情况。

**Benefits of Multi-Process**: The primary benefits are:多进程的优势：主要优势在于：

- **Stability**: If a web page (renderer process) crashes or leaks memory, it doesn't crash the whole browser - you can close that tab and the rest stays alive. In one-process browsers, a single bad script could tear down everything. Chrome can show the "Aw, Snap" error for a single tab when its process dies, and you can reload it independently.稳定性：如果某个网页（渲染器进程）崩溃或发生内存泄漏，不会导致整个浏览器崩溃——你可以关闭该标签页，其余部分仍可正常运行。在单进程浏览器中，一个恶意脚本就可能导致整个浏览器瘫痪。当某个标签页的进程终止时，Chrome 会显示"哎呀，出错了"的提示，你可以独立重新加载该标签页。
- **Security (Sandboxing)**: By running web content in a restricted process, the browser can limit what that code can do on your system. Even if an attacker finds a vulnerability in the rendering engine, they are trapped in the sandbox - the renderer process typically cannot read your files or arbitrarily open network connections or launch programs. It must request the browser process for things like file access, which can be validated or denied. This sandbox is enforced at the OS level (using job objects, seccomp filters, etc. depending on platform).安全性（沙盒机制）：通过在受限进程中运行网页内容，浏览器可以限制代码对系统的操作权限。即使攻击者发现了渲染引擎的漏洞，他们也会被困在沙盒中——渲染器进程通常无法读取你的文件、随意建立网络连接或启动程序。它必须通过浏览器进程请求文件访问等操作，这些请求可以被验证或拒绝。这种沙盒机制在操作系统层面实施（根据平台不同，使用作业对象、seccomp 过滤器等）。
- **Performance Isolation**: Intensive work in one tab (a heavy webapp or an infinite loop) is mostly confined to that tab's renderer process. Other tabs (different process) can remain responsive because their processes aren't blocked. Also, the OS can schedule processes on different CPU cores - so two heavy pages can run in parallel on a multi-core system better than if they were threads of one process.性能隔离：一个标签页中的密集操作（如繁重的网页应用或无限循环）主要被限制在该标签页的渲染进程内。其他标签页（不同进程）能够保持响应，因为它们的进程不会被阻塞。此外，操作系统可以将进程调度到不同的 CPU 核心上——因此，在多核系统中，两个繁重的页面可以并行运行，效果优于它们作为同一进程的线程运行的情况。
- **Memory segmentation**: Each process has its own address space, so memory is not shared. This prevents one site from snooping on data of another and also means when a tab is closed, the OS can reclaim all memory from that process efficiently. The downside is some overhead due to duplicated resources and processes (each renderer loads its own copy of the JS engine, etc.).内存分段：每个进程拥有独立的地址空间，因此内存不共享。这既防止了某个站点窥探其他站点的数据，也意味着当标签页关闭时，操作系统能高效回收该进程占用的全部内存。其弊端在于重复资源和进程会带来额外开销（每个渲染器需加载独立的 JavaScript 引擎副本等）。

**Site Isolation**: Initially, Chrome's model was one process per tab. Over time they evolved it to one process per site (especially after Spectre - see next section on security). As of 2024, site isolation is enabled by default for 99% of Chrome users across desktop platforms, with Android support continuing to be refined. This means if you have two tabs both open to [example.com](https://example.com/), Chrome might decide to use one process for both (to save memory, because they're the same site and thus less risky to put together). But a tab with [example.com](https://example.com/) and an iframe of [evil.com](https://evil.com/) would by default put [evil.com](https://evil.com/)'s iframe in a separate process from the parent page (to protect the [example.com](https://example.com/) data). This enforcement is what Chrome calls "Strict Site Isolation" (launched around Chrome 67 as a default). Site isolation causes Chrome to use 10-13% more system resources due to increased process creation, but provides crucial security benefits.站点隔离：最初，Chrome 的模型是每个标签页一个进程。随着时间的推移，他们将其发展为每个网站一个进程（尤其是在 Spectre 漏洞出现后——详见安全章节）。截至 2024 年，桌面平台上 99%的 Chrome 用户默认启用了站点隔离功能，Android 平台的支持也在持续完善。这意味着，如果你同时打开两个都访问 example.com 的标签页，Chrome 可能会决定让这两个标签页共用一个进程（以节省内存，因为它们是同一站点，放在一起风险较低）。但如果一个标签页包含 example.com 和 evil.com 的 iframe，Chrome 默认会将 evil.com 的 iframe 与父页面分配到不同进程（以保护 example.com 的数据）。这种强制机制就是 Chrome 所称的"严格站点隔离"（自 Chrome 67 版本起默认启用）。由于进程创建数量增加，站点隔离会导致 Chrome 多消耗 10%-13%的系统资源，但能提供至关重要的安全效益。

Firefox's architecture, called [Electrolysis](https://blog.mozilla.org/addons/2016/04/11/the-why-of-electrolysis/) (e10s), was historically one content process for all tabs (for many years Firefox was single-process and only enabled a few content processes around 2017). As of 2021, Firefox uses multiple content processes (by default 8 for web content). With [Project Fission](https://blog.mozilla.org/security/2021/05/18/introducing-site-isolation-in-firefox/) (site isolation), Firefox is moving toward isolating sites similarly - it can spin up new processes for cross-site iframes, and in Firefox 108+ they enabled site isolation by default, increasing the number of processes to potentially one per site like Chrome. Firefox also has a GPU process (for WebRender and compositing) and a separate networking process, similar to Chrome's split. So in practice, Firefox now has a very Chrome-like model: a parent process, a GPU process, a network process, a few content (renderer) processes, and some utility processes (for extensions, media decoding, etc. - e.g. a media plugin can run isolated).Firefox 的架构名为 Electrolysis（e10s），历史上所有标签页共享一个内容进程（多年来 Firefox 一直是单进程架构，直到 2017 年左右才启用少量内容进程）。截至 2021 年，Firefox 已采用多内容进程模式（默认 8 个进程用于网页内容）。通过 Project Fission（站点隔离）项目，Firefox 正朝着类似的方向隔离站点——它能为跨站 iframe 创建新进程，并在 Firefox 108+版本中默认启用站点隔离，使进程数量可能达到每个站点一个（类似 Chrome）。Firefox 还设有 GPU 进程（用于 WebRender 和合成渲染）以及独立的网络进程，这与 Chrome 的拆分方式相似。因此实际上，Firefox 现在拥有与 Chrome 高度相似的模型：一个父进程、一个 GPU 进程、一个网络进程、若干内容（渲染器）进程，以及一些实用进程（用于扩展、媒体解码等——例如媒体插件可独立运行）。

Safari (WebKit) likewise moved to a multi-process model (WebKit2) where each tab's content is in a separate WebContent process and a central UI process controls them. Safari's WebContent processes are also sandboxed and cannot directly access devices or files without going through the UI process. Safari also has a networking process that is shared (and possibly other helpers). So while implementations differ, the concept is consistent: isolate each webpage's code in its own sandboxed environment.Safari（WebKit）同样转向了多进程模型（WebKit2），每个标签页的内容运行在独立的 Web 内容进程中，并由一个中央 UI 进程进行控制。Safari 的 Web 内容进程同样采用沙盒机制，必须通过 UI 进程才能访问设备或文件。Safari 还设有共享的网络进程（可能还有其他辅助进程）。因此，尽管具体实现方式存在差异，其核心理念是一致的：将每个网页的代码隔离在独立的沙盒环境中运行。

One important point is inter-process communication (IPC): How do these processes talk to each other? Browsers use IPC mechanisms (on Windows, often named pipes or other OS IPC; on Linux, maybe Unix domain sockets or shared memory; Chrome has its own IPC library Mojo). For example, when a network response arrives in the Network process, it needs to be delivered to the correct Renderer process (via the Browser process coordinating). Similarly, when you do a DOM fetch(), the JS engine will call into a network API which sends a request to the Network process and so on. IPC adds complexity, but browsers optimize heavily (e.g. using shared memory for transferring large data like images efficiently, and posting asynchronous messages to avoid blocking).一个关键点是进程间通信（IPC）：这些进程之间如何相互通信？浏览器使用 IPC 机制（在 Windows 上，通常采用命名管道或其他操作系统 IPC；在 Linux 上，可能使用 Unix 域套接字或共享内存；Chrome 拥有自己的 IPC 库 Mojo）。例如，当网络响应到达网络进程时，需要通过浏览器进程协调，将其传递给正确的渲染进程。同样，当你执行 DOM 的 fetch()操作时，JavaScript 引擎会调用网络 API，向网络进程发送请求等。IPC 增加了复杂性，但浏览器对此进行了大量优化（例如，使用共享内存高效传输图像等大型数据，并通过异步消息传递避免阻塞）。

**Process Allocation Strategies**: Chrome doesn't always create a brand new process for every single tab - there are limits (particularly on devices with low memory, it may reuse processes for same-site tabs). Chrome will reuse an existing renderer if you open another tab to the same site, to conserve memory (this is why sometimes two tabs of the same site share process). It also has a limit on total processes (which can scale based on RAM). When the limit is hit, it might start putting multiple unrelated sites in one process, though it tries hard to avoid mixing sites if site isolation is enabled. On Android, Chrome uses fewer processes because of the memory constraints (often a max of 5-6 processes for content).进程分配策略：Chrome 并非始终为每个标签页创建全新进程——存在限制（尤其在内存较低的设备上，可能会为同站标签页复用进程）。当用户打开同一网站的新标签页时，Chrome 会复用现有渲染器以节省内存（这就是为何同一网站的两个标签页有时会共享进程）。此外，Chrome 对总进程数设有上限（该上限可根据内存大小动态调整）。当达到上限时，系统可能将多个无关网站合并至同一进程，但在启用站点隔离的情况下，Chrome 会尽量避免混合不同站点。在安卓平台上，受内存限制，Chrome 使用的进程数更少（内容进程通常最多 5-6 个）。

One more concept in Chromium is **servicification**: splitting browser components into services that could run in separate processes. For example, the Network Service was made a separate module that can run out-of-process. The idea is modularity - powerful systems can run each service in its own process, whereas constrained devices might consolidate some services back into one process to save overhead. Chrome can decide at runtime or build time how to deploy these services. As noted in the snippet, on high-end it might split everything (UI, net, GPU, etc. all separate), and on low-end (Android) it might combine browser & network in one process to cut down overhead.Chromium 中还有一个概念是服务化：将浏览器组件拆分为可在独立进程中运行的服务。例如，网络服务被设计为可独立运行的模块。其核心理念在于模块化——高性能系统可以让每个服务在独立进程中运行，而资源受限设备则可将部分服务合并到同一进程以降低开销。Chrome 可在运行时或构建时决定如何部署这些服务。如代码片段所示，高端设备可能将所有组件（UI、网络、GPU 等）完全分离，而低端设备（如 Android）则可能将浏览器与网络合并到同一进程以减少开销。

The takeaway: Chromium's architecture is designed to run the browser UI and each site in different sandboxes, using processes as the isolation boundary. Firefox and Safari have converged on similar designs. This architecture greatly improves security and reliability at the cost of more memory usage. The web content processes are treated as untrusted, and that's where site isolation (next section) comes into play to even isolate different origins from each other within separate processes.要点：Chromium 的架构设计将浏览器界面和每个网站分别运行在不同的沙盒中，以进程作为隔离边界。Firefox 和 Safari 也采用了类似的设计。这种架构在牺牲更多内存使用的前提下，大幅提升了安全性和可靠性。网页内容进程被视为不可信，而站点隔离（下一节）正是通过将不同来源的网页内容分别隔离到独立进程中，进一步强化了这种防护。

## Site Isolation and Sandboxing站点隔离与沙盒机制

Site isolation and sandboxing are security features that build on the multi-process foundation. They aim to ensure that even if malicious code runs in the browser, it cannot easily steal data from other sites or access your system.站点隔离和沙盒机制是基于多进程架构的安全特性。它们旨在确保即使恶意代码在浏览器中运行，也无法轻易窃取其他网站的数据或访问你的系统。

**Site Isolation**: We've touched on this - it means that different websites (different sites, more strictly) run in different renderer processes. Chrome's site isolation was boosted after the [Spectre vulnerability](https://developer.chrome.com/blog/meltdown-spectre) came to light in 2018. Spectre showed that malicious JavaScript could potentially read memory it shouldn't (by exploiting CPU speculative execution). If two sites were in the same process, a malicious site could use Spectre to snoop on memory of the sensitive site (like your banking site). The only robust solution is to not let them share a process at all. So Chrome made site isolation a default: every site gets its own process, including cross-origin iframes. Firefox has followed with Project Fission (enabled by default in recent versions), which aims for the same - they cite isolating every site in its own process for security. This is a significant change from the past where if you had a parent page and multiple iframes from various domains, they might all live in one process (especially if they were in one tab). Now, those iframes would be split so that e.g. an \<iframe src="[https://evil.com](https://evil.com/)"> on a good site page is forced into a different process, preventing even low-level attacks from leaking info between them.网站隔离：我们之前提到过——这意味着不同网站（更严格地说，是不同站点）会在不同的渲染进程中运行。Chrome 的网站隔离功能在 2018 年 Spectre 漏洞曝光后得到了加强。Spectre 漏洞表明，恶意 JavaScript 可能通过利用 CPU 推测执行机制，读取本不应访问的内存数据。如果两个网站处于同一进程中，恶意网站就能利用 Spectre 漏洞窥探敏感网站（如你的银行网站）的内存数据。唯一可靠的解决方案就是不让它们共享任何进程。因此 Chrome 将网站隔离设为默认功能：每个网站都拥有独立进程，包括跨源 iframe。Firefox 也通过 Project Fission 项目（近期版本中默认启用）实现了相同目标——他们宣称要将每个网站隔离在独立进程中以保障安全。这与过去的情况形成鲜明对比：过去父页面和来自不同域名的多个 iframe 可能全部运行在同一个进程中（尤其是当它们位于同一标签页时）。现在这些 iframe 会被拆分，例如在正常网站页面中的\<iframe src="https://evil.com">会被强制分配到不同进程。防止即使是低级别的攻击在它们之间泄露信息。

From a developer point of view, site isolation is mostly transparent. One implication is that communications between an embedded iframe and its parent might cross process boundaries now, so things like postMessage between them are implemented via IPC under the hood. But the browser makes this seamless; you as a dev just use the APIs as normal.从开发者的角度来看，站点隔离基本上是透明的。一个影响是，嵌入的 iframe 与其父页面之间的通信现在可能会跨越进程边界，因此它们之间的 postMessage 等操作实际上是通过 IPC 实现的。但浏览器使这一切无缝衔接；作为开发者，你只需正常使用 API 即可。

**Sandboxing**: Each renderer process (and other auxiliary processes) run in a sandbox with restricted privileges. For example, on Windows, Chrome uses a job object and drops privileges so the renderer can't call most Win32 APIs that access the system. On Linux, it uses namespaces and seccomp filters to limit syscalls. The renderer basically can compute and render content but if it tries to open a file or camera or microphone, it will be blocked (unless going through proper channels that ask user permission via the browser process). WebKit's documentation explicitly notes that WebContent processes have no direct access to filesystem, clipboard, devices, etc. - they must request via the UI process which mediates. This is why, for example, when a site tries to use your microphone, the permission prompt is shown by the browser UI (browser process) and if allowed, the actual recording is done in a controlled process. The sandbox is a crucial line of defense. Even if an attacker finds a bug to run native code in the renderer, they then face the sandbox barrier - they'd need a separate exploit (an "escape") to break out to the system. This layered approach (called site isolation + sandbox) is state-of-the-art for browser security.沙盒机制：每个渲染进程（及其他辅助进程）都在权限受限的沙盒中运行。例如在 Windows 系统中，Chrome 通过作业对象并降低权限，使渲染器无法调用大多数访问系统的 Win32 API。在 Linux 系统中，则通过命名空间和 seccomp 过滤器限制系统调用。渲染器基本只能执行计算和渲染任务，若尝试打开文件、摄像头或麦克风，将被阻止（除非通过浏览器进程请求用户授权的正规渠道）。WebKit 文档明确指出，WebContent 进程无法直接访问文件系统、剪贴板、设备等资源——必须通过 UI 进程进行中介请求。这就是为何当网站试图调用麦克风时，权限提示由浏览器界面（浏览器进程）显示，若获授权，实际录音将在受控进程中完成。沙盒是至关重要的防御屏障。即便攻击者找到漏洞在渲染器中运行原生代码，仍需突破沙盒限制——他们需要另寻漏洞（即"逃逸"手段）才能入侵系统。 这种分层方法（称为站点隔离+沙箱）是浏览器安全领域的最先进技术。

Firefox's sandboxing is also quite strict now (it was weaker in early e10s days but they ramped it up). Firefox content processes can't directly access much either; and Firefox also sandboxes the GPU process to handle graphics driver issues.Firefox 的沙盒机制现在也相当严格（在早期 e10s 时代较弱，但后来已大幅加强）。Firefox 的内容进程同样无法直接访问太多内容；此外，Firefox 还对 GPU 进程进行沙盒化处理，以应对图形驱动问题。

**Out-of-Process iframes (OOPIF)**: In Chrome's implementation of site isolation, they invented the term [OOPIF](https://www.chromium.org/developers/design-documents/oop-iframes/) for out-of-process iframe. From a user's perspective, nothing changes, but in Chrome's internal architecture, each frame of a page can potentially be backed by a different renderer process. The top-level frame and same-site frames share one process; cross-site frames use different processes. All those processes "cooperate" to render a single tab's content, coordinated by the browser process. This is pretty complex, but Chrome has a frame tree that can span processes. It means your one tab might be running N processes (one for the main document, others for each cross-site subdocument). They communicate via IPC for things like DOM events crossing the boundary or certain JavaScript calls that involve cross-context. The web platform (through specs like [COOP/COEP](https://web.dev/articles/coop-coep), [SharedArrayBuffer,](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/SharedArrayBuffer) etc.) is evolving with these constraints in mind after Spectre.进程外 iframe（OOPIF）：在 Chrome 的站点隔离实现中，他们创造了 OOPIF 这个术语来指代进程外 iframe。从用户视角看，一切照旧，但在 Chrome 内部架构中，页面的每个框架都可能由不同的渲染进程支撑。顶层框架与同站框架共享一个进程，跨站框架则使用独立进程。所有这些进程在浏览器进程的协调下"协同工作"，共同渲染单个标签页的内容。这种机制相当复杂，但 Chrome 拥有可跨进程运作的框架树结构。这意味着你的一个标签页可能运行着 N 个进程（一个用于主文档，其余用于每个跨站子文档）。它们通过 IPC 进行通信，处理诸如跨越边界的 DOM 事件或涉及跨上下文的特定 JavaScript 调用。在 Spectre 漏洞之后，Web 平台（通过 COOP/COEP、SharedArrayBuffer 等规范）正基于这些约束条件持续演进。

**Memory and Performance Costs**: Site isolation does increase memory usage because more processes are used. Chrome devs noted it could be a 10-20% memory [overhead](https://www.thurrott.com/mobile/chrome-os/162980/spectre-mitigation-increases-chrome-memory-usage-google-says) in some cases. They mitigated some by something called "best-effort process consolidation" for same-site, and by limiting how many processes can be spawned (we mentioned earlier). Firefox initially didn't isolate every site due to memory concerns but after Spectre they found ways to do it more efficiently with 8-privileged-process limit and on-demand process creation. Safari historically has a strong process model but I'm not sure if it isolates cross-site iframes; WebKit2 certainly isolates top-level pages. Apple's focus is often also on privacy (Intelligent Tracking Prevention will partition cookies, etc.), but that's a different layer.内存与性能成本：站点隔离确实会增加内存占用，因为使用了更多进程。Chrome 开发者指出，在某些情况下可能导致 10-20%的内存开销。他们通过"尽力而为的进程合并"策略（针对同站点）以及限制可生成的进程数量（前文已提及）来缓解这一问题。Firefox 最初因内存考量未对所有站点实施隔离，但在 Spectre 漏洞事件后，他们找到了更高效的实现方式——通过 8 个特权进程上限和按需创建进程的机制。Safari 历来拥有强大的进程模型，但我不确定它是否对跨站 iframe 进行隔离；WebKit2 确实对顶级页面实施了隔离。苹果的侧重点往往也在于隐私保护（智能防追踪技术会隔离 Cookie 等），但这属于不同层面的防护。

Cross-site prefetches are limited for privacy reasons and will currently only work if the user has no cookies set for the destination site, preventing sites from tracking user activity via prefetched pages that may never be visited.出于隐私原因，跨站预取功能受到限制，目前仅在用户未为目标站点设置 cookie 时才能生效，从而防止网站通过可能永远不会被访问的预取页面来追踪用户活动。

All in all, site isolation ensures that the principle of least privilege is applied: code from origin A cannot access data from origin B unless via web APIs with explicit consent (like postMessage or storage that's partitioned). And the sandbox ensures that even if code is rogue, it can't touch your system directly. These measures make browser exploits much harder - an attacker typically needs multiple chain exploits now (one to break renderer, one to escape sandbox) to do serious damage, which raises the bar significantly.总而言之，站点隔离确保了最小权限原则的实施：来自源 A 的代码无法访问源 B 的数据，除非通过获得明确许可的 Web API（如 postMessage 或分区存储）。而沙盒机制则确保即使代码存在恶意行为，也无法直接接触你的系统。这些措施大大增加了浏览器漏洞利用的难度——攻击者现在通常需要组合多个漏洞链（一个突破渲染进程，一个逃逸沙盒）才能造成实质性破坏，这显著提高了攻击门槛。

As a web developer, you might not directly feel site isolation, but you benefit from it through a safer web. One thing to be aware of is that cross-origin interactions might have slightly more overhead (because of IPC) and that some optimizations like in-process script sharing aren't possible across origins. But browsers are continuously optimizing the messaging between processes to minimize any performance hit.作为网页开发者，你可能不会直接感受到站点隔离带来的影响，但你会通过更安全的网络环境从中受益。需要注意的是，跨源交互可能会产生略微更高的开销（由于进程间通信），并且某些优化措施（如进程内脚本共享）无法跨源实现。不过浏览器正在持续优化进程间的消息传递机制，以最大限度降低性能影响。

Now, after covering security, let's turn to tools and performance instrumentation - essentially, how we developers can peek into this pipeline and measure or debug it.现在，在介绍完安全性之后，我们来谈谈工具和性能检测——本质上，就是我们开发者如何窥探这个管道，并对其进行测量或调试。

## Comparing Chromium, Gecko, and WebKit对比 Chromium、Gecko 与 WebKit

We've mainly described Chrome/Chromium's behavior (Blink engine for HTML/CSS, V8 for JS, multi-process via Aura/Chromium infrastructure). Other major engines - Mozilla's Gecko (used in Firefox) and Apple's WebKit (used in Safari) - share the same fundamental goals and a broadly similar pipeline, but there are noteworthy differences and historical divergences.我们主要描述了 Chrome/Chromium 的行为（HTML/CSS 采用 Blink 引擎，JS 使用 V8，通过 Aura/Chromium 基础设施实现多进程）。其他主流引擎——Mozilla 的 Gecko（用于 Firefox）和 Apple 的 WebKit（用于 Safari）——虽然共享相同的基本目标和大致相似的流程，但在具体实现和历史演变上存在显著差异。

**Shared Concepts**: All engines parse HTML into a DOM, parse CSS into style data, compute layout, and paint/composite. All have JS engines with JITs and garbage collection. And all modern ones are multi-process (or at least multi-threaded) for parallelism and security.共享概念：所有引擎都将 HTML 解析为 DOM，将 CSS 解析为样式数据，计算布局，并进行绘制/合成。所有引擎都配备带有即时编译和垃圾回收机制的 JavaScript 引擎。所有现代引擎都采用多进程（或至少多线程）架构以实现并行性和安全性。

**Differences in CSS/Style SystemCSS/样式系统的差异**

One interesting difference is how CSS style computation is implemented by rendering engine:一个有趣的差异在于渲染引擎实现 CSS 样式计算的方式：

- **Blink (Chromium)**: Uses a single-threaded style engine in C++ (historically based on WebKit's). It computes style sequentially for the DOM tree. It has had incremental style invalidation optimizations, but by and large it's one thread doing the work (apart from some minor parallelization in animation).Blink（Chromium）：采用 C++编写的单线程样式引擎（历史上基于 WebKit）。它按顺序为 DOM 树计算样式。虽然具备增量式样式失效优化，但总体而言是由单个线程完成工作（动画部分有少量并行处理除外）。
- **Gecko (Firefox)**: In the Quantum project (2017), Firefox integrated Stylo, a new CSS engine written in Rust, which is multi-threaded. Firefox can calculate style for different DOM subtrees in parallel using all CPU cores. This was a major performance improvement for CSS in Gecko. So, style recalculation in Firefox might use 4 cores to do what Blink does on 1. This is one advantage of Gecko's approach (at the cost of complexity).Gecko（Firefox）：在 2017 年的 Quantum 项目中，Firefox 集成了 Stylo——一个用 Rust 编写的新 CSS 引擎，支持多线程。Firefox 能够利用所有 CPU 核心并行计算不同 DOM 子树的样式。这是 Gecko 在 CSS 性能上的重大提升。因此，Firefox 的样式重计算可能使用 4 个核心完成 Blink 在单核上执行的任务。这是 Gecko 方案的优势之一（代价是复杂性增加）。
- **WebKit (Safari)**: WebKit's style engine is single-threaded like Blink (since Blink forked from WebKit in 2013, they shared architecture up to that point). WebKit has done interesting things like a bytecode JIT for CSS selectors matching. It may transform CSS selectors into bytecode and JIT compile a matcher for speed. Blink did not adopt that (it uses iterative matching).WebKit（Safari）：WebKit 的样式引擎与 Blink 一样是单线程的（由于 Blink 于 2013 年从 WebKit 分支，两者在此前的架构相同）。WebKit 曾尝试创新，例如为 CSS 选择器匹配引入字节码 JIT 技术。它可能将 CSS 选择器转换为字节码，并通过 JIT 编译匹配器来提升速度。Blink 并未采用此方案（仍使用迭代匹配）。

So, in CSS, Gecko stands out with parallel style computation via Rust. Blink and WebKit rely on optimized C++ and maybe some JIT tricks (in WebKit's case).因此，在 CSS 领域，Gecko 凭借 Rust 实现的并行样式计算脱颖而出，而 Blink 和 WebKit 则依赖优化的 C++代码，以及 WebKit 特有的 JIT 技巧。

**Layout and Graphics布局与图形**

All three engines implement the CSS box model and layout algorithms. Specific features might land in one before others (e.g. at one time WebKit was ahead in CSS Grid support, then Blink caught up - often they share code through standards bodies).所有三大引擎均实现了 CSS 盒模型及布局算法。某些特定功能可能会率先落地于某一引擎（例如，WebKit 曾一度在 CSS 网格支持方面领先，随后 Blink 迎头赶上——两者常通过标准机构共享代码）。

Firefox (Gecko) made a huge change by introducing **WebRender** as its compositor/rasterizer. WebRender is now the default rendering engine in Firefox and has contributed to significant performance improvements, particularly for graphics-intensive web content. WebRender (also Rust) basically takes the display list and renders it on the GPU directly, handling things like tessellating shapes, text, etc. with the GPU. It's like moving more painting work to the GPU. In Chrome's pipeline, rasterization is still done on CPU (for most content) then sent to GPU as bitmaps. WebRender tries to avoid making bitmaps for whole layers and instead draw vectors on GPU (except for text glyphs which it caches as atlas textures). This means Firefox can potentially animate more content at high performance because it doesn't need to re-rasterize everything if only small portions change - it can redraw via GPU very quickly. It's akin to how a game engine redraws a scene every frame using GPU calls. The downside is it's complex to implement and tune, and can stress the GPU more. But as GPU power grows, this approach is forward-looking. Chrome's team considered a similar approach ("SKIA GPU" path) but has not done a full WebRender style overhaul.Firefox（Gecko）通过引入 WebRender 作为合成器/光栅化器，实现了重大变革。WebRender 现已成为 Firefox 的默认渲染引擎，显著提升了性能表现，尤其对图形密集型网页内容效果显著。WebRender（同样基于 Rust 语言）本质上将显示列表直接交由 GPU 渲染，利用 GPU 处理形状细分、文本渲染等任务，相当于将更多绘制工作转移至 GPU。在 Chrome 的渲染管线中，光栅化仍由 CPU 完成（针对大多数内容），随后以位图形式传输至 GPU。而 WebRender 则避免为整个图层生成位图，转而直接在 GPU 上绘制矢量图形（文本字形除外，会缓存为图集纹理）。这意味着当页面仅局部发生变化时，Firefox 无需重新光栅化全部内容，可通过 GPU 快速重绘，从而以高性能实现更多动画效果。其运作原理类似游戏引擎每帧通过 GPU 调用重绘场景。不足之处在于实现与调优过程复杂，且可能增加 GPU 负载。但随着 GPU 性能持续提升，这种方案具有前瞻性。Chrome 团队曾考虑过类似的方法（"SKIA GPU"路径），但并未进行完整的 WebRender 式全面改造。

Safari (WebKit) uses an approach more similar to older Chrome: it has a converts the compositor with layers (called CALayer, since on Mac and iOS it uses Core Animation layers). Safari was early to move to GPU compositing (iPhone OS and Safari 4 in 2009 had hardware-accelerated compositing for certain CSS like transforms). Safari and Chrome diverged but conceptually both do tiling and compositing. Safari also offloads a lot to the GPU (and uses tiling, especially on iOS where tile drawing was fundamental for smooth scrolling).Safari（WebKit）采用的方式更接近旧版 Chrome：它将合成器与图层（称为 CALayer，因为在 Mac 和 iOS 上使用 Core Animation 图层）进行转换。Safari 较早转向 GPU 合成（2009 年的 iPhone OS 和 Safari 4 已对某些 CSS 属性如变换实现了硬件加速合成）。Safari 和 Chrome 虽已分化，但概念上两者都采用分块与合成技术。Safari 还将大量工作卸载到 GPU（并采用分块技术，尤其在 iOS 上，分块绘制是实现流畅滚动的关键）。

**Mobile optimizations**: Each engine has special cases for mobile. For example, WebKit has the concept of tile coverage for scrolling (used in iOS's UIWebView historically). Chrome on Android uses "tiling" and tries to keep raster tasks minimal to hit frame rates. Firefox's WebRender came from the mobile-first Servo project.移动端优化：每个引擎都有针对移动端的特殊处理。例如，WebKit 引入了滚动时的瓦片覆盖概念（历史上用于 iOS 的 UIWebView）。Android 版 Chrome 采用“瓦片化”策略，并尽量保持光栅化任务的最小化以达到帧率要求。Firefox 的 WebRender 源自移动优先的 Servo 项目。

**JavaScript EnginesJavaScript 引擎**

- **V8 (Chromium)** we described: Ignition, Sparkplug, TurboFan, Maglev as of 2023.V8（Chromium）我们已描述过：截至 2023 年，其包含 Ignition、Sparkplug、TurboFan、Maglev 等组件。
- **SpiderMonkey (Firefox)**: It historically had an interpreter, then a Baseline JIT and an optimizing JIT (IonMonkey). Since Firefox 83 (2021), IonMonkey has been fully replaced by WarpMonkey, which builds on CacheIR data rather than a separate type inference system. Current tiers are: Baseline Interpreter, Baseline JIT, and WarpMonkey as the top-tier optimizing compiler. SpiderMonkey also has a different GC (also generational, called Incremental GC since 2012, and now mostly incremental/concurrent).SpiderMonkey（Firefox）：历史上它曾有一个解释器，随后又加入了基线 JIT 和优化 JIT（IonMonkey）。自 Firefox 83（2021 年）起，IonMonkey 已被 WarpMonkey 完全取代，后者基于 CacheIR 数据而非独立的类型推断系统。当前层级包括：基线解释器、基线 JIT，以及作为顶级优化编译器的 WarpMonkey。SpiderMonkey 还采用了不同的垃圾回收机制（同样为分代式，自 2012 年起称为增量 GC，目前主要采用增量/并发模式）。
- **JavaScriptCore (Safari)**: As noted, it has 4 tiers (LLInt, Baseline, DFG, FTL). It uses a different GC (WebKit's GC is a generational mark-sweep called Butterfly or Boehm variations historically, now bmalloc etc.). JSC's FTL uses LLVM to optimize, which is unique (V8 and SM have their own compilers, JSC leverages LLVM for one tier). This can yield very fast code, but the compilation is heavy. JSC tends to prioritize peak performance on certain benchmarks (it often shines on some, but V8 tends to catch up; they leapfrog).JavaScriptCore（Safari）：如前所述，它拥有 4 个层级（LLInt、Baseline、DFG、FTL）。它使用不同的垃圾回收机制（WebKit 的 GC 是一种分代标记清除算法，历史上称为 Butterfly 或 Boehm 变体，现在使用 bmalloc 等）。JSC 的 FTL 利用 LLVM 进行优化，这是其独特之处（V8 和 SM 使用自己的编译器，而 JSC 在某一层级借助 LLVM）。这可以生成非常高效的代码，但编译开销较大。JSC 倾向于在某些基准测试中追求峰值性能（它常在某些测试中表现出色，但 V8 往往能迎头赶上；两者交替领先）。

In terms of ES features, all three engines are pretty much up-to-date with the latest standards, thanks to test262 and each other's competition.在 ES 特性方面，得益于 test262 测试套件和彼此间的竞争，三大引擎基本都已跟上最新标准。

**Multi-Process Model Differences多进程模型差异**

- **Chrome**: each tab typically separate, site isolation at origin level, lots of processes (can be dozens).Chrome：每个标签页通常独立运行，在源级别进行站点隔离，进程数量众多（可达数十个）。
- **Firefox**: fewer processes by default (8 content processes handling all tabs, plus more if needed for cross-site iframes with Fission). So, it's not necessarily one process per tab; tabs share content processes in a pool. This means Firefox might have lower memory usage under many-tab scenarios, but it also means one content process crash can take out multiple tabs (though it tries to group by site, so maybe all Facebook tabs in one process, etc.).Firefox：默认使用较少的进程（8 个内容进程处理所有标签页，若启用 Fission，跨站 iframe 可能需要更多进程）。因此，并非每个标签页对应一个独立进程；标签页共享一个内容进程池。这意味着 Firefox 在打开大量标签页时内存占用可能更低，但同时也意味着一个内容进程崩溃可能导致多个标签页同时失效（不过它会尝试按站点分组，例如所有 Facebook 标签页可能集中在同一个进程中）。
- **Safari**: likely one process per tab (or per a few tabs) - on iOS, WKWebView definitely isolates each webview. Safari desktop historically did each tab separate as well. Not sure if they isolate cross-origin iframes yet - Apple hasn't talked about Spectre mitigations much, but Safari does have process per domain for top-level at least.Safari：很可能每个标签页（或每几个标签页）对应一个独立进程——在 iOS 上，WKWebView 明确隔离每个 Web 视图。桌面版 Safari 历来也为每个标签页分配独立进程。目前尚不确定它是否隔离跨源 iframe——苹果对 Spectre 漏洞缓解措施讨论不多，但 Safari 至少对顶级域名实现了按域分配进程。

**Interprocess Coordination**: All engines have to solve similar problems like how to implement alert() (which blocks JS) in a multi-process environment - typically the browser process shows the alert UI and pauses that script context. Or how to handle prompt/confirm, how to do Modal dialogs, etc. There are subtle differences (e.g. Chrome doesn't truly block the thread for alert - it spins a nested runloop in the renderer, etc. whereas Firefox might still freeze that tab's process).进程间协调：所有引擎都必须解决类似的问题，例如如何在多进程环境中实现 alert()（它会阻塞 JavaScript）——通常浏览器进程会显示 alert 界面并暂停该脚本上下文。或者如何处理 prompt/confirm、模态对话框等。各引擎存在细微差异（例如 Chrome 不会真正阻塞 alert 线程——它会在渲染器中旋转一个嵌套运行循环，而 Firefox 可能会冻结该标签页的进程）。

**Crash handling**: Chrome and Firefox both have crash reporters that can restart a crashed content process and show an error in the tab. Safari's Web Content process crash typically will display a simpler error message in the content area.崩溃处理：Chrome 和 Firefox 都有崩溃报告器，可以重启崩溃的内容进程并在标签页中显示错误。Safari 的 Web 内容进程崩溃通常会在内容区域显示更简单的错误信息。

**Feature Implementation Divergence功能实现差异**

Some web platform features are engine-specific: e.g. The View Transitions API (formerly experimental in Chrome) reached Baseline Newly Available status in October 2025, with same-document transitions now supported across Chrome 111+, Edge 111+, Firefox 133+, and Safari 18+. Cross-document transitions (for multi-page apps) are supported in Chrome 126+, Edge 126+, and Safari 18.2+, with Firefox support still pending.某些 Web 平台功能是引擎特有的：例如 View Transitions API（最初在 Chrome 中实验性推出）于 2025 年 10 月达到 Baseline 新可用状态，其中同文档过渡现已在 Chrome 111+、Edge 111+、Firefox 133+ 和 Safari 18+ 中得到支持。跨文档过渡（用于多页面应用）在 Chrome 126+、Edge 126+ 和 Safari 18.2+ 中得到支持，Firefox 的支持仍在等待中。

**Developer tools**: Chrome's DevTools is very advanced. Firefox's DevTools also very good (with some unique features like CSS Grid highlighters early on, shape editor). Safari's Web Inspector is fine but not as full-featured in some areas. These differences can matter to devs debugging in each browser.开发者工具：Chrome 的 DevTools 非常先进。Firefox 的 DevTools 也很出色（早期就拥有 CSS 网格高亮器、形状编辑器等独特功能）。Safari 的 Web Inspector 表现尚可，但在某些领域功能不够全面。这些差异对需要在不同浏览器中进行调试的开发者来说至关重要。

**Performance Trade-offs性能权衡**

Historically, Chrome was lauded for faster JS and overall performance due to multi-process and V8. Firefox with Quantum closed a lot of gaps, sometimes surpassing Chrome in graphics (WebRender can be very fast for complex pages). Safari often excels in graphics and low power usage on Apple hardware (they optimize for power a lot).历史上，Chrome 因多进程架构和 V8 引擎在 JavaScript 执行速度及整体性能上备受赞誉。Firefox 的 Quantum 项目大幅缩小了差距，有时在图形处理方面甚至超越 Chrome（WebRender 在处理复杂页面时速度极快）。Safari 在苹果硬件上通常表现出色，尤其在图形性能和低功耗方面（其针对能耗进行了大量优化）。

**Memory**: Chrome has a reputation for high memory usage (all those processes). Firefox tries to be a bit more conservative. Safari is very memory efficient on iOS out of necessity (limited RAM), and they do a lot of memory optimization in WebKit.内存：Chrome 以高内存占用著称（所有那些进程）。Firefox 则试图更保守一些。Safari 在 iOS 上出于必要性（有限的 RAM）而非常注重内存效率，并且他们在 WebKit 中做了大量内存优化。

**External Contributors**: Interesting note - a lot of improvements in these engines come from external teams like Igalia (e.g. implementing CSS Grid in both WebKit and Blink). So sometimes features land roughly simultaneously.外部贡献者：有趣的是——这些引擎的许多改进来自外部团队，比如 Igalia（例如，在 WebKit 和 Blink 中实现 CSS Grid）。因此，有时功能会大致同时落地。

From a web developer's perspective, the differences often manifest as:从网页开发者的角度来看，差异通常表现为：

- Needing to test on all engines because there might be slight differences or bugs in one's implementation of a CSS feature or an API.需要在所有引擎上进行测试，因为某个引擎在实现 CSS 特性或 API 时可能存在细微差异或漏洞。
- Performance might differ (for example, a particular JS workload might be faster in one engine than another due to JIT heuristics).性能可能有所不同（例如，由于 JIT 启发式算法的差异，某个特定的 JavaScript 工作负载在一个引擎中可能比另一个引擎运行得更快）。
- Some APIs might not be available in one (Safari is often last to implement some new APIs like WebRTC or IndexedDB versions, etc. though they eventually do).某些 API 可能在某些引擎中不可用（例如 Safari 通常最后才实现一些新 API，如 WebRTC 或 IndexedDB 的某些版本，不过最终它们还是会支持）。

But the core concepts we discussed (network -> parse -> layout -> paint -> composite -> JS execution) apply to all, just with varying internal approaches or names:但我们讨论的核心概念（网络→解析→布局→绘制→合成→JS 执行）适用于所有情况，只是内部实现方式或命名有所不同

- In Gecko: parse -> frame tree -> display list -> WebRender scene or layer tree (if WebRender disabled) -> composite.在 Gecko 中：解析 -> 帧树 -> 显示列表 -> WebRender 场景或层树（若 WebRender 禁用）-> 合成。
- In WebKit: parse -> render tree -> graphics layers -> composite (via CoreAnimation).在 WebKit 中：解析 -> 渲染树 -> 图形层 -> 合成（通过 CoreAnimation）。

And all have analogous subsystems (DOM, styling, layout, graphics, JS engine, networking, processes/threads).所有浏览器都有类似的子系统（DOM、样式、布局、图形、JS 引擎、网络、进程/线程）。

Knowing these helps in debugging: e.g. if something is janky in Safari but not Chrome, it could be WebKit's painting differs. Or if CSS is slow in Firefox, maybe it's hitting a path that isn't parallelized by Stylo (though that's rare).了解这些有助于调试：例如，如果某个功能在 Safari 中出现卡顿但在 Chrome 中没有，可能是 WebKit 的绘制方式不同。或者如果 CSS 在 Firefox 中运行缓慢，可能是触发了 Stylo 未并行化的路径（尽管这种情况很少见）。

To sum up, while Chromium, Gecko, and WebKit have different implementations and even some different innovations (parallel CSS in Gecko, WebRender GPU, etc.), they increasingly implement the same web standards and even collaborate on many. The choice of engine matters more for the platform vendors and open web diversity, but as a developer you mostly care that your site runs everywhere. Under the hood, each engine's unique architecture might lead to different performance profiles or bugs, which is why testing and using performance diagnostics in each (like Firefox's performance tool vs Chrome's) can be insightful. It's beyond our scope to list all differences, but hopefully this gives an idea of the landscape: they are convergent in high-level design (multi-process, similar pipelines) yet divergent in specific technical solutions.总结来说，尽管 Chromium、Gecko 和 WebKit 在实现方式上存在差异，甚至各自拥有不同的创新（如 Gecko 的并行 CSS、WebRender GPU 等），但它们越来越多地遵循相同的网络标准，甚至在许多方面展开合作。引擎的选择对平台供应商和开放网络的多样性更为重要，但作为开发者，你主要关心的是你的网站在各处都能正常运行。在底层，每个引擎独特的架构可能导致不同的性能表现或错误，这就是为什么在每个引擎中进行测试并使用性能诊断工具（如 Firefox 的性能工具与 Chrome 的对比）会很有价值。列出所有差异超出了本文范围，但希望这能让你对整体格局有所了解：它们在高层设计上趋于一致（多进程、相似的流水线），但在具体技术解决方案上各有千秋。

## Conclusion and Further Reading结论与延伸阅读

We've journeyed through the life of a web page inside a modern browser - from the moment a URL is entered, through networking and navigation, HTML parsing, styling, layout, painting, and JavaScript execution, all the way to the GPU putting pixels on the screen. We've seen that browsers are essentially mini operating systems: managing processes, threads, memory, and a slew of complex subsystems to ensure web content loads fast and runs securely. For web developers, understanding these internals can demystify why certain best practices (like minimizing reflows or using async scripts) matter for performance, or why some security policies (like not mixing origins in iframes) exist.我们已完整走过了现代浏览器中一个网页的生命周期——从输入 URL 的那一刻起，历经网络通信与导航、HTML 解析、样式计算、布局绘制、JavaScript 执行，直至 GPU 将像素呈现在屏幕上。我们看到浏览器本质上就是微型操作系统：管理进程、线程、内存以及一系列复杂的子系统，以确保网页内容快速加载且安全运行。对于 Web 开发者而言，理解这些内部机制能揭示为何某些最佳实践（如减少重排或使用异步脚本）对性能至关重要，也能解释为何存在某些安全策略（如不在 iframe 中混用不同源）。

A few key takeaways for developers:给开发者的一些关键要点：

**Optimize network usage**: Fewer round trips and smaller files = faster start render. The browser can do a lot (HTTP/2, caching, speculative loading) but you should still leverage techniques like resource hints and efficient caching. The networking stack is high-performance, but latency is always a killer.优化网络使用：更少的往返次数和更小的文件 = 更快的首屏渲染。浏览器能处理很多事情（HTTP/2、缓存、预加载），但你仍应善用资源提示和高效缓存等技术。网络协议栈性能虽高，但延迟始终是致命问题。

**Structure your HTML/CSS for efficiency**: A well-structured DOM and lean CSS (avoid very deep trees or overly complex selectors) can help the parsing and style systems. Understand that CSS and DOM build computed style, then layout computes geometry - heavy DOM manipulations or style changes can trigger these recalculations.高效组织 HTML/CSS：结构良好的 DOM 和精简的 CSS（避免过深的层级或过于复杂的选择器）有助于解析和样式系统。需理解 CSS 与 DOM 构建计算样式，随后布局计算几何信息——频繁的 DOM 操作或样式变更可能触发这些重新计算。

**Batch DOM updates**: to avoid repeated style/layout thrash. Use DevTools Performance panel to catch when your script is causing many layouts or paints.批量 DOM 更新：避免重复的样式/布局抖动。使用 DevTools 性能面板来捕捉脚本导致大量布局或绘制的情况。

**Use compositing-friendly CSS for animations**: Animations of transform or opacity stay off the main thread and on the compositor, yielding smooth animations. Avoid animating layout-bound properties if possible.使用利于合成的 CSS 进行动画：对 transform 或 opacity 的动画会脱离主线程并在合成器上运行，从而实现流畅的动画。如有可能，避免对布局相关的属性进行动画处理。

**Mind the JS execution**: Though JS engines are super-fast, long tasks will block the main thread. Break up long operations (so the page stays responsive) and in some cases consider Web Workers for background tasks. Also, remember that heavy JS can cause GC pauses (rarely long nowadays, but can happen if memory balloons).注意 JS 执行：尽管 JS 引擎速度极快，但长时间任务会阻塞主线程。请拆分长操作（以保持页面响应），某些情况下可考虑使用 Web Workers 处理后台任务。同时需注意，繁重的 JS 可能导致 GC 暂停（如今虽罕见长时间暂停，但内存膨胀时仍可能发生）。

**Security features**: Embrace them - e.g. use iframe sandbox or rel=noopener when appropriate, because you now know the browser will isolate those anyway; cooperating with it is good.安全特性：善用它们——例如在适当情况下使用 iframe 沙盒或 rel=noopener，因为你现在知道浏览器无论如何都会隔离这些内容；与之配合是明智之举。

**DevTools is your friend**: The performance and network panels in particular are gold mines for seeing exactly what the browser is doing. If something is slow or janky, the tools often point to the cause (a long layout, a slow paint, etc.).开发者工具是你的好帮手：尤其是性能面板和网络面板，它们是观察浏览器具体行为的金矿。如果遇到卡顿或迟缓，这些工具通常能指出原因（如布局耗时过长、绘制缓慢等）。

**For those eager to dive even deeper, an excellent resource is Browser Engineering by Pavel Panchekha and Chris Harrelson (available at** [browser.engineering](http://browser.engineering/)**).**对于那些渴望更深入探索的人来说，Pavel Panchekha 和 Chris Harrelson 合著的《浏览器工程》（可在 browser.engineering 获取）是一份极好的资源。

It's essentially a free online book that guides you through building a simple web browser, covering networking, HTML/CSS parsing, layout, and more in an accessible way. It can serve as a more in-depth companion to everything we discussed, solidifying knowledge by example. Additionally, the Chrome team's multi-part series "[Inside look at modern web browser](https://developer.chrome.com/blog/inside-browser-part1)" provides a readable overview with diagrams. The V8 blog ([v8.dev](http://v8.dev/)) and [Mozilla's Hacks blog](https://hacks.mozilla.org/) are great for learning about engine advances (e.g. new JIT compiler tiers or WebRender internals).这本质上是一本免费在线书籍，以通俗易懂的方式引导你构建一个简易网页浏览器，涵盖网络通信、HTML/CSS 解析、页面布局等内容。它可以作为我们讨论内容的深度拓展读物，通过实例巩固知识。此外，Chrome 团队的多篇系列文章《现代浏览器内部探秘》配有图解，提供了可读性强的概述。V8 博客（v8.dev）和 Mozilla 的 Hacks 博客是了解引擎技术进展（如新型 JIT 编译器层级或 WebRender 内部机制）的绝佳资源。

In conclusion, modern browsers are marvels of software engineering. They successfully abstract away all this complexity so that as developers we mostly just write HTML/CSS/JS and trust the browser to handle it. Yet, by peering under the hood, we gain insights that help us write more performant, robust applications. We appreciate why certain techniques improve user experience (e.g. avoiding blocking the main thread, or reducing unnecessary DOM complexity) because we see how the browser has to work under the covers. The next time you debug a webpage or wonder why Chrome or Firefox behaves a certain way, you'll have a mental model of the browser's internals to guide you.总之，现代浏览器是软件工程的奇迹。它们成功地将所有这些复杂性抽象化，使得我们作为开发者大多只需编写 HTML/CSS/JS，并信任浏览器来处理一切。然而，通过深入探究其底层机制，我们能够获得洞见，从而编写出性能更优、更健壮的应用程序。我们理解某些技术为何能改善用户体验（例如避免阻塞主线程，或减少不必要的 DOM 复杂度），因为我们看到了浏览器在幕后必须如何运作。下次当你调试网页或好奇 Chrome 或 Firefox 为何表现出某种行为时，你将拥有一个浏览器内部机制的思维模型来指引你。

Happy building, and remember that the web platform's depth rewards those who explore it - there's always more to learn, and tools to help you learn it.快乐构建，并记住，网络平台的深度会回报那些探索它的人——总有更多值得学习的内容，以及帮助你学习的工具。
